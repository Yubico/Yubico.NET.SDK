### #2 Required UV composes inconsistent CTAP request (YESDK-1610) - audit severity MED
- Verdict: CONFIRMED-WITH-CORRECTION | My severity: MED. The contradictory fields are real in both PIN and built-in UV branches; obtaining a token using built-in UV is valid on CTAP 2.1+. The audit's old backend name is obsolete; at HEAD it is `WebAuthnBackend`.
- Location at HEAD: `src/WebAuthn/src/Client/UserVerification/UvDecision.cs:93-111`; `Client/WebAuthnClient.Registration.cs:298-335`; `Client/WebAuthnClient.Authentication.cs:216-255`; `Client/WebAuthnBackend.cs:124-139,180-199`; `src/Fido2/src/Cbor/FidoSessionRequestEncoding.cs:46-55,85-95,100-156` (old monolithic client and backend locations drifted).
- Spec / contract: “Platforms MUST NOT include both the "uv" option key and the pinUvAuthParam parameter in the same request.” — CTAP 2.3 §6.1 (local `ctap23.txt:760`). “Platforms MUST NOT include both "uv" and pinUvAuthParam parameters in same request.” — §6.2 (`ctap23.txt:1375`). “Instead, platforms SHOULD create a pinUvAuthParam by obtaining pinUvAuthToken via getPinUvAuthTokenUsingUvWithPermissions or getPinUvAuthTokenUsingPinWithPermissions, as appropriate.” — §6.1 (`ctap23.txt:755-756`).
- Reference implementations: `python-fido2/fido2/client/__init__.py:670-740` returns a token OR internal_uv (`uv=true` only in the no-token legacy path), `:833-855,1000-1008` emits `uv` only for internal_uv and pin_auth only for a token.
- Evidence: Required+PIN returns `UseToken=true,UvOption=true`; built-in UV returns the same combination. Builders place `uv` in options and compute `PinUvAuthParam`; backend copies both and Fido2 encoder emits both. Independently, registration backend converts absent `uv` to nullable `false` at line 125 and encoder serializes the false key; assertion backend preserves absence at lines 180-184, so the audit's claim applies to makeCredential **only**, not getAssertion.
- Repro: `AuditV2/WebAuthnAuditReproTests.cs:YESDK1610_RegistrationTokenDoesNotAlsoRequestUv` (PIN/UV variants), `YESDK1610_AssertionTokenDoesNotAlsoRequestUv` (PIN/UV variants) — FAILED as expected: “CTAP ... must not contain both the uv option and pinUvAuthParam”. `YESDK1610_BackendPreservesAbsentUvOption(true)` — FAILED as expected: expected null, actual false; `(false)` — passed (assertion backend already preserves absence). Repros capture the backend request/options, not independently decoded wire bytes; encoder at lines cited establishes the CBOR mapping.
- Remediation: Set `UvOption=null` whenever `UseToken=true` in `UvDecision.cs`; in `WebAuthnBackend.MakeCredentialAsync` retain nullable absence (`request.Options?.TryGetValue("uv", out ...)`), as the assertion method already does. Preserve the no-token legacy `uv=true` option if ever used. Update existing tests expecting Required+PIN `uv=true` (`WebAuthnClientMakeCredentialTests.cs:299`, `WebAuthnClientGetAssertionTests.cs:264`).
- API impact: none (internal transport behavior). Proving test: all YESDK1610 repro cases, including the passing absence control. Depends on / interacts with: exclude-list preflight #25 (which uses token + `up=false`, no `uv`). Open decisions: none.

### #6 Attestation None forwards authenticator statement (YESDK-1614) - audit severity MED
- Verdict: CONFIRMED-WITH-CORRECTION | My severity: MED. L3 does **not** require zeroing AAGUID on none; its change log explicitly says it is no longer zeroed (`webauthn3.txt:10360-10361`).
- Location at HEAD: `src/WebAuthn/src/Client/WebAuthnClient.Registration.cs:339-380`; default None is `Client/Registration/RegistrationOptions.cs:64` (old monolithic location drifted).
- Spec / contract: “If the authenticator generates an attestation statement that is not a self attestation, the client will replace it with a None attestation statement.” — WebAuthn L3 §5.4.7 (`webauthn3.txt:4073-4079`). “Set the value of credentialCreationData.attestationObjectResult.fmt to "none", and set the value of credentialCreationData.attestationObjectResult.attStmt to be an empty CBOR map.” — §5.1.3 (`:2387-2399`). The exception is exactly “If the aaguid in the attested credential data is 16 zero bytes, credentialCreationData.attestationObjectResult.fmt is "packed", and "x5c" is absent from credentialCreationData.attestationObjectResult, then self attestation is being used and no further action is needed.” — §5.1.3 (`:2394`). L3 §5.1.3 does **not** require nor prescribe changing AAGUID for none; “The client MAY replace the aaguid and attestation statement with a more privacy-friendly ... version” is under **indirect**, not none (`:2400-2403`).
- Reference implementations: `python-fido2/fido2/client/__init__.py:915-925` builds attestation object from the raw authenticator response without checking `options.attestation` (same apparent gap in this standalone library); `client/windows.py:180-198,273-286` forwards preference to Windows platform API, so Windows handling is external. Reference behavior is not proof of WebAuthn L3 compliance.
- Evidence: builder reads authenticator `AttestationStatement`, creates attestation object unchanged, returns raw bytes and statement; `options.Attestation` is never read. Test supplies packed signature and a nonzero AAGUID, and decodes returned attestation object.
- Repro: `AuditV2/WebAuthnAuditReproTests.cs:YESDK1614_NoneAttestationRemovesAuthenticatorStatement` — FAILED as expected: expected fmt `none`, actual `packed`.
- Remediation: In `BuildRegistrationResponse` use none format with empty CBOR map for non-self statements if `options.Attestation == None`, keeping credential ID and AAGUID intact as L3 specifies; ensure all returned statement/raw object representations agree. Handle L3 self-attestation exception explicitly; other preferences need separate policy review.
- API impact: none (response values change to promised preference). Proving test: YESDK1614 repro. Depends on / interacts with: attestation format and extension output parsing. Open decisions: whether direct/enterprise/indirect should retain current pass-through; recommend scope fix to None and document remaining semantics separately.

### #7 Preferred resident key not requested (YESDK-1615) - audit severity MED
- Verdict: CONFIRMED-WITH-CORRECTION | My severity: MED. The audit is correct that a capable device receives `rk=false`, but incorrect that the WebAuthn builder emits a dictionary `rk=false`: it emits **no entry**, then the backend converts absence to nullable false and the Fido2 encoder emits the key.
- Location at HEAD: `src/WebAuthn/src/Client/WebAuthnClient.Registration.cs:84-85,282-335` (`rk=true` only Required); `Client/WebAuthnBackend.cs:124`; `src/Fido2/src/Cbor/FidoSessionRequestEncoding.cs:100-118`.
- Spec / contract: “If the authenticator is capable of client-side credential storage modality ... Let requireResidentKey be true.” — WebAuthn L3 §5.1.3, `residentKey` preferred branch (`webauthn3.txt:2218-2236`). If incapable or capability unknown, “Let requireResidentKey be false.” — same section (`:2234-2236`).
- Reference implementations: `python-fido2/fido2/client/__init__.py:828-845` sets `rk=true` for Preferred and `info.options.get("rk")`, otherwise omits `rk`. `client/windows.py:180,273-286` passes `prefer_resident_key` to the Windows API separately.
- Evidence: GetInfo supplies `Options["rk"]` but builder ignores it. Backend `request.Options?.TryGetValue("rk", out var rk) == true && rk` assigns `false` even on absent key; encoder writes bool whenever nullable has a value.
- Repro: `AuditV2/WebAuthnAuditReproTests.cs:YESDK1615_PreferredResidentKeyOnCapableAuthenticatorRequestsDiscoverable` — FAILED as expected: capable authenticator did not receive `rk:true`; `YESDK1615_BackendPreservesAbsentResidentKeyOption` — FAILED as expected: expected null, actual false. Hardware repro written but NOT run: `AuditV2/WebAuthnAuditHardwareReproTests.cs:YESDK1615_PreferredResidentKeyCanBeDiscoveredWithoutAllowList`, requires touch and known test PIN; the expected failure is that a preferred-rk registration cannot be found in a discoverable assertion. It does not delete credentials/reset the device; it creates a credential, and other existing discoverable credentials are ignored by ID matching.
- Remediation: pass GetInfo capability into `BuildMakeCredentialRequest`; use `rk=true` for Required or Preferred on a device advertising `rk:true`; omit `rk` otherwise. Preserve nullable absence in `WebAuthnBackend.cs` rather than coercing to false.
- API impact: none; new discoverable credentials persist on capable authenticators (storage consumption). Proving test: both YESDK1615 unit tests plus human-run hardware test. Depends on / interacts with: credential-management storage limits and credProps extension. Open decisions: whether unknown capability should omit the key or explicitly send false; recommend omit, matching Python and spec's effective false.

### #9 Ceremony timeout ignored (YESDK-1617) - audit severity MED
- Verdict: CONFIRMED | My severity: MED.
- Location at HEAD: `src/WebAuthn/src/Client/Registration/RegistrationOptions.cs:66-69`; `Client/Authentication/AuthenticationOptions.cs:59-66`; `Client/WebAuthnClient.Registration.cs:49-126`; `Client/WebAuthnClient.Authentication.cs:52-118`. No `CancelAfter` or linked cancellation deadline exists in WebAuthn source; the caller token is simply forwarded.
- Spec / contract: “If pkOptions.timeout is present, check if its value lies within a reasonable range as defined by the client and if not, correct it to the closest value lying within that range. Set a timer lifetimeTimer to this adjusted value.” — WebAuthn L3 §5.1.3 (`webauthn3.txt:2020-2023`) and §5.1.4 (`:2607-2610`). “If lifetimeTimer expires, For each authenticator in issuedRequests invoke the authenticatorCancel operation ...” — §5.1.3 (`:2170-2176`) / §5.1.4 (`:2720-2726`). SDK AuthenticationOptions.xml additionally says “The timeout applies to the entire operation, including user interaction.” (`AuthenticationOptions.cs:63-65`).
- Reference implementations: `python-fido2/fido2/client/__init__.py:1117-1142,1155-1161` starts a Timer that sets the event after timeout on make/get and cancels timer on completion; `libfido2/src/dev.c:599-604` exposes per-device transport timeout (not the same per-ceremony WebAuthn policy).
- Evidence: no reads of either options.Timeout in the client; caller cancellation is honored but no automatic ceremony deadline. Test fake holds a real backend operation until its token is canceled; a 1-second guard prevents hanging, then verifies it was the guard, not the requested 50-ms timeout, that canceled.
- Repro: `AuditV2/WebAuthnAuditReproTests.cs:YESDK1617_RegistrationTimeoutCancelsPendingAuthenticator` and `YESDK1617_AuthenticationTimeoutCancelsPendingAuthenticator` — both FAILED as expected: “the ceremony deadline, not the test guard, must cancel”.
- Remediation: create linked cancellation source with bounded `options.Timeout` at the public ceremony entry, start before backend/prompt calls, pass its token throughout, dispose after entire ceremony; map deadline expiration to NotAllowed while preserving caller cancellation. Define range/default deliberately (authentication XML currently promises no timeout for null, unlike spec's default).
- API impact: behavioral change; no signature change. Proving test: both YESDK1617 repros (and follow-up caller cancellation/default tests). Depends on / interacts with: PIN prompt timeout and `MatchedCredential.SelectAsync` deferred selection. Open decisions: keep documented null=no timeout (non-browser SDK choice) vs spec default; recommend explicitly document the divergence if retained. Define whether deferred selection is inside the deadline.

### #25 Nonpositive WebAuthn batch size (YESDK-1634 sub-item) - audit severity MED
- Verdict: CONFIRMED-WITH-CORRECTION | My severity: LOW for conforming hardware, MED for a malicious or buggy GetInfo response. A conforming authenticator cannot report zero/negative; the SDK currently accepts both as int without validating the protocol field.
- Location at HEAD: `src/Fido2/src/AuthenticatorInfo.cs:365-367` reads CBOR integer into nullable int with no positive-range validation; `src/WebAuthn/src/Client/WebAuthnClient.Registration.cs:248-255` passes GetInfo to `Internal/ExcludeListPreflight.cs:94-110,125-143`. Preflight is only invoked with nonempty exclude list **and** token (`:241-244`).
- Spec / contract: “maxCredentialCountInList (0x07) Unsigned Integer Optional ... Maximum number of credentials supported in credentialID list at a time by the authenticator. MUST be greater than zero if present.” — CTAP 2.3 §6.4 (`ctap23.txt:1931-1935`). No requirement to accommodate invalid GetInfo values; rejecting malformed responses is a valid alternative to clamping.
- Reference implementations: `python-fido2/fido2/client/__init__.py:584-608` uses `info.max_creds_in_list or 1` (zero defaults to 1; negative is truthy in Python and would remain invalid). `yubikit-android/fido/.../Ctap2Client.java:880-896,918-930` uses `count ?? 1` without validation; zero leads to empty chunk (same class of bug).
- Evidence: `maxCreds = MaxCredentialCountInList ?? 1` retains 0 or -1; `Math.Min(maxCreds, remaining)` yields nonpositive, `Skip(offset).Take(chunkSize)` empty. Empty fake probe sent; if authenticator reports NoCredentials, `offset += chunkSize` makes no progress for zero or moves backwards for negative, so loop can run indefinitely until externally canceled. This test deliberately fails at empty probe to avoid hanging.
- Repro: `AuditV2/WebAuthnAuditReproTests.cs:YESDK1634_NonpositiveGetInfoListLimitStillProbesAllCredentials(0/-1)` — both FAILED as expected: `Assert.NotEmpty() Failure: Collection was empty`.
- Remediation: Prefer validate `maxCredentialCountInList` as positive unsigned in `AuthenticatorInfo.Decode` and reject malformed GetInfo before any ceremony (negative values as well); alternatively clamp to >=1 in preflight to preserve forward progress with faulty devices. If rejecting at decoder, replace the repro with a decode-boundary contract test and assert a clear typed error.
- API impact: none (malformed device responses now fail earlier). Proving test: both YESDK1634 repros if clamping, or revised decoder rejection test. Depends on / interacts with: #2 token preflight and malformed GetInfo validation. Open decisions: reject vs clamp; recommend reject at decoder because spec says unsigned/positive, plus a local progress guard against accidental zero.
