# Audit v2 — B (extensions)

### #1 WebAuthn PRF is not translated to CTAP hmac-secret (YESDK-1609) - audit severity MED
- Verdict: CONFIRMED-WITH-CORRECTION | My severity: MED. The SDK does have a working `PrfInput.ComputeSalt` helper and a *separate* low-level `WithHmacSecret(protocol, sharedSecret, keyAgreement, salts)` encoder. Neither is called from PRF processing. The auditor's overall conclusion is correct, but these subcomponents do exist; `WithHmacSecretMakeCredential()` also exists, though it only sends a boolean instead of the §12.8 input map.
- Location at HEAD: `src/WebAuthn/src/Extensions/ExtensionPipeline.cs:74-79,126-131,230-242,321-333`; `src/WebAuthn/src/Extensions/Adapters/PrfAdapter.cs:30-69,74-129`; `src/Fido2/src/Extensions/Prf/PrfInput.cs:62-79`; `src/Fido2/src/Extensions/Shared/ExtensionBuilder.cs:140-204,214-218,230-250,367-409`; `src/Fido2/src/Cbor/FidoSessionRequestEncoding.cs:75-83`. No meaningful drift from audit.
- Spec / contract: “Set hmac-secret to true in the authenticator extensions input.” (registration); “Let salt1 be the value of SHA-256(UTF8Encode(\"WebAuthn PRF\") || 0x00 || ev.first).” and “Send an hmac-secret extension to the authenticator using the values of salt1 and, if set, salt2 as the parameters of the same name in that process. Decrypt the extension result and set results to the PRF result(s), if any.” — WebAuthn L3 §10.1.4. “The hmac-secret extension provides two PRFs per credential: one which is used for requests where user verification is performed and another for all other requests. This extension only exposes a single PRF per credential and, when implementing on top of hmac-secret, that PRF MUST be the one used for when user verification is performed.” — §10.1.4. “keyAgreement(0x01): public key of platform key-agreement key.”, “saltEnc(0x02): Encryption of the one or two salts”, “saltAuth(0x03): authenticate(shared secret, saltEnc)” — CTAP 2.3 §12.7 (NOT §12.5 in this copy). “This extension is only applicable for authenticatorMakeCredential, and the hmac-secret extension MUST also be present with the value of \"hmac-secret\" set to true.” and “This extension input is the same as the hmac secret extension’s getAssertion input” — CTAP 2.3 §12.8.
- Reference implementations: `python-fido2/fido2/ctap2/extensions.py:169-170,197-246,280-324,328-371` hashes inputs, selects credential, negotiates key agreement, encrypts/authenticates salt, decrypts output and reports `enabled`/`results`; `libfido2/src/cbor.c:728,746,914` sends hmac-secret true at registration, hmac-secret-mc map when applicable and hmac-secret map at assertion.
- Evidence: registration `WithPrf()` serializes `{"prf":{}}`, not `{"hmac-secret":true}`; registration eval is discarded, so no `hmac-secret-mc`. Authentication writes raw First/Second into literal `{"prf":{"eval":...}}`, with no contextual hash, key agreement, salt encryption/authentication, or output decryption; `ParseAuthenticationOutput` searches for literal `prf.eval` instead of encrypted `hmac-secret`. No capability check or UV-for-PRF enforcement in extension adapter. Existing `FidoPrfTests.cs:192-225` explicitly performs an assertion *without* extension inputs or verifying PRF output; its name is misleading.
- Repro: `Fido2AuditReproTests.YESDK1609_RegistrationPrfRequestsHmacSecret` — FAILED as expected: expected `hmac-secret`, got `prf`. `WebAuthnAuditReproTests.YESDK1609_AuthenticationPrfUsesEncryptedHmacSecretNotLiteralPrf` — FAILED as expected: expected `hmac-secret`, got `prf`.
- Hardware repro: `WebAuthnAuditHardwareTests.YESDK1609_PrfRoundTripProducesStable32ByteResult`; requires PIN and touch, **built but not run**. Run only with human/device coordination: `dotnet toolchain.cs -- test --integration --project WebAuthn --filter "FullyQualifiedName~YESDK1609_PrfRoundTripProducesStable32ByteResult&Category=RequiresUserPresence"`. This test uses a nondiscoverable credential and does not delete any credential; whether it succeeds on the available device after correction is unverified.
- Remediation: perform feature detection on GetInfo, use `hmac-secret:true` at registration; with eval and support for §12.8, send `hmac-secret-mc` map and decrypt result. At assertion select matching evalByCredential or fallback eval, hash both inputs, negotiate shared secret and pass into existing encryption/authentication methods, request user verification, decrypt `hmac-secret` output and return WebAuthn results. Enforce secret ownership/zeroing. Update misleading low-level `WithPrf` contract to take required protocol/session context rather than emit fictitious CTAP `prf`; avoid a second competing encoder.
- API impact: likely breaking for direct `ExtensionBuilder.WithPrf` if removing unsupported CTAP representation; WebAuthn call shape can remain unchanged. Proving tests: the two map repros, and hardware round-trip (plus new deterministic fake-session cryptographic request/response test during implementation). Depends on / interacts with: #26a,b and PRF user-verification policy; #11 is independent. Open decisions: whether to deprecate/remove direct `WithPrf` (recommend remove/replace with session-aware API), whether to support registration-time eval on §12.8 capable authenticators (recommend yes), and how to select among multiple credentials (probe then bind salts to selected ID).

### #11 credBlob assertion retrieval uses wrong CBOR type (YESDK-1619) - audit severity MED
- Verdict: CONFIRMED | My severity: MED.
- Location at HEAD: `src/Fido2/src/Extensions/Shared/ExtensionBuilder.cs:43,75-79,307-311`; `src/Fido2/src/Cbor/FidoSessionRequestEncoding.cs:80-83`; `src/WebAuthn/src/Extensions/WebAuthnExtensionInputs.cs:38-47`; `src/WebAuthn/src/Extensions/ExtensionPipeline.cs:117-146,292-305`; `src/Fido2/tests/Yubico.YubiKit.Fido2.IntegrationTests/FidoCredBlobTests.cs:129-155`. No meaningful drift.
- Spec / contract: “get() : A boolean value to indicate that this extension is requested by the Relying Party.” and “partial dictionary AuthenticationExtensionsClientInputs { boolean getCredBlob; };” and “authenticatorGetAssertion authenticator extension input ... \"credBlob\":true” — CTAP 2.3 §12.2. “authenticatorMakeCredential ... \"credBlob\": Byte String containing the credBlob value” — same section.
- Reference implementations: `python-fido2/fido2/ctap2/extensions.py:487-498` writes bytes only at creation and `{"credBlob": True}` for getCredBlob; `libfido2/src/cbor.c:713,908` similarly writes bytes for creation and bool true for assertion.
- Evidence: existing integration test calls `WithCredBlob(ReadOnlyMemory<byte>.Empty)` for getAssertion; the builder always writes `WriteByteString` (CBOR h''), and the request encoder copies it unchanged under key 4. WebAuthn cannot request retrieval because `AuthenticationExtensionInputs` has no GetCredBlob; its output parser checking unrequested `credBlob` does not cause retrieval. Existing hardware test only conditionally asserts when an extension response exists; it can succeed without retrieving anything, so no additional duplicate hardware test was added.
- Repro: `Fido2AuditReproTests.YESDK1619_GetAssertionCredBlobUsesBooleanTrue` — FAILED as expected: `ReadBoolean()` encountered CBOR major type 2 (byte string). `WebAuthnAuditReproTests.YESDK1619_WebAuthnOffersGetCredBlobClientInput` — FAILED as expected: GetCredBlob public property absent.
- Hardware repro: existing `FidoCredBlobTests.CredBlob_StoreAndRetrieve_ReturnsStoredData` requires touch/PIN and is NOT RUN; existing result assertion is conditional and should be made unconditional during the production fix. Proposed command after strengthening: `dotnet toolchain.cs -- test --integration --project Fido2 --filter "FullyQualifiedName~CredBlob_StoreAndRetrieve_ReturnsStoredData&Category=RequiresUserPresence"`.
- Remediation: add `ExtensionBuilder.WithGetCredBlob()` writing boolean true solely for getAssertion while retaining `WithCredBlob(blob)` for registration. Expose `GetCredBlob` on `AuthenticationExtensionInputs` and wire the pipeline; verify the response as WebAuthn `getCredBlob` output (not just low-level `credBlob`). Strengthen the current integration test to require the response extension and expected blob.
- API impact: additive. Proving tests: both repros and strengthened existing hardware test. Depends on / interacts with: none. Open decisions: whether to rename WebAuthn output from `CredBlob` to `GetCredBlob` (recommend additive alias/new member during breaking window rather than silently conflate create/get outputs).

### #26a Credential-specific PRF inputs ignored (YESDK-1634) - audit severity MED
- Verdict: CONFIRMED | My severity: MED.
- Location at HEAD: `src/Fido2/src/Extensions/Prf/PrfInput.cs:53-60`; `src/WebAuthn/src/Extensions/Adapters/PrfAdapter.cs:44-68`; `src/Fido2/src/Extensions/Shared/ExtensionBuilder.cs:385-409`.
- Spec / contract: “If evalByCredential is present and contains an entry whose key is the base64url encoding of the credential ID that will be returned, let ev be the value of that entry. If ev is null and eval is present, then let ev be the value of eval.” — WebAuthn L3 §10.1.4.
- Reference implementations: `python-fido2/fido2/ctap2/extensions.py:197-219,345-349` validates allowed IDs, selects matching per-credential input after credential selection and falls back to global eval. `PreviewSignExtension` is unrelated.
- Evidence: adapter passes original input without selecting key; builder reads First/Second only; a per-credential override with global eval produces byte-for-byte identical output to global-only; map-only enters `WriteStartMap(1)` for eval but writes no first field and throws `InvalidOperationException: Not at end of the definite-length data item` at `WriteEndMap`. Also see #1: even global encoding isn't valid CTAP.
- Repro: `Fido2AuditReproTests.YESDK1634_CredentialSpecificPrfOverridesGlobalInput` — FAILED as expected: collections equal; `YESDK1634_OnlyCredentialSpecificPrfEncodesWithoutFailure` and `WebAuthnAuditReproTests.YESDK1634_PrFOnlyCredentialMapIsSelectedForMatchingAllowCredential` — FAILED as expected: definite-length map not complete.
- Remediation: select matched credential before composing encrypted salts; validate keys against allowCredentials and reject non-empty per-credential map with empty allowCredentials; use fallback eval if unmatched. Do not serialize the WebAuthn eval map as CTAP. API impact: none if selecting in WebAuthn layer; direct low-level WithPrf requires redesign under #1. Proving tests: map-only and override repros with selection-aware cryptographic integration test. Depends on / interacts with: #1. Open decisions: how to probe multiple credentials without touching (recommend python-fido2-style preselection or explicitly reject unsupported multi-credential requests rather than choose first).

### #26b PRF enabled ignores returned value (YESDK-1634) - audit severity MED
- Verdict: CONFIRMED-WITH-CORRECTION | My severity: MED. The adapter actually looks for a literal `prf` entry, *not* the specified `hmac-secret` boolean. Its presence-only behavior is independently wrong even for its current fictional wire format.
- Location at HEAD: `src/WebAuthn/src/Extensions/Adapters/PrfAdapter.cs:74-84`.
- Spec / contract: “Set enabled to the value of hmac-secret in the authenticator extensions output. If not present, set enabled to false.” — WebAuthn L3 §10.1.4. “true if, and only if, the PRF is available for use with the created credential.” — §10.1.4.
- Reference implementations: `python-fido2/fido2/ctap2/extensions.py:315-324` reads `extensions.get("hmac-secret", False)` and returns that boolean.
- Evidence: `TryGetValue("prf", out rawValue)` ignores `rawValue` and returns `Enabled:true`; `prf:false` yields false positive, while legitimate `hmac-secret:false` produces null.
- Repro: `WebAuthnAuditReproTests.YESDK1634_PrFRegistrationFalseOutputIsNotEnabled` — FAILED as expected: expected false, got true with `prf:false`.
- Remediation: when PRF requested, parse CTAP `hmac-secret` boolean strictly; return Enabled:false if absent; decrypt optional `hmac-secret-mc` result when requested. API impact: none. Proving test: adapter false/missing/true response cases plus #1 registration map. Depends on / interacts with: #1. Open decisions: malformed nonboolean authenticator output handling (recommend reject or report disabled, never claim enabled).

### #26c Missing previewSign attestation substitutes authentication key (YESDK-1634) - audit severity MED
- Verdict: CONFIRMED | My severity: HIGH because an application may persist the wrong public key/handle as a distinct signing key.
- Location at HEAD: `src/WebAuthn/src/Extensions/Adapters/PreviewSignAdapter.cs:175-241`; `src/WebAuthn/src/Extensions/PreviewSign/GeneratedSigningKey.cs:20-52`.
- Spec / contract: “This authenticator registration extension and authentication extension allows a Relying Party to sign arbitrary data using an asymmetric key pair associated with a credential but different from the credential key pair.” — [Yubico draft sign extension v4](https://yubicolabs.github.io/webauthn-sign-extension/4/) §10.2.1. Registration processing requires “keyHandle: An ArrayBuffer containing a copy of innerAuthData.attestedCredentialData.credentialId.”, “publicKey: An ArrayBuffer containing a copy of innerAuthData.attestedCredentialData.credentialPublicKey.”, and “Let origAttObj be unsignedExtOutputs[\"previewSign\"][att-obj] parsed as a CBOR map.” — §10.2.1. `AuthenticationExtensionsSignGeneratedKey` declares “required ArrayBuffer attestationObject;” — §10.2.1.
- Reference implementations: `python-fido2/fido2/ctap2/extensions.py:743-769` requires unsigned key 7, parses inner attestation and takes ONLY inner credential data; `Yubico.NET.SDK-Legacy/Yubico.YubiKey/src/Yubico/YubiKey/Fido2/PreviewSignExtensionMethods.cs:33-48` returns null if unsigned output absent (never substitutes authentication credential).
- Evidence: unsigned output missing triggers fallback at :226-240, constructing GeneratedSigningKey with the *outer authentication credential's* ID/public key and null attestation. Existing nearby tests cover valid unsigned attestation, not missing unsigned plus valid outer AT data.
- Repro: `WebAuthnAuditReproTests.YESDK1634_PreviewSignMissingInnerAttestationDoesNotSubstituteCredentialKey` — FAILED as expected: expected WebAuthnClientError, no exception thrown (outer AT credential was substituted).
- Remediation: remove fallback; reject incomplete requested previewSign output (or return null, but never substitute keys), require correctly parsed inner attestation. API impact: none if exception; `GeneratedSigningKey.AttestationObject` could become nonnullable in a breaking cleanup. Proving test: missing-unsigned repro plus existing valid-unsigned adapter tests. Depends on / interacts with: none. Open decisions: throw InvalidState vs omit extension result for incomplete response (recommend InvalidState to prevent silent key misbinding).

### #26d FIDO previewSign discards credential IDs and chooses first params (YESDK-1634) - audit severity MED
- Verdict: CONFIRMED | My severity: MED. This is the *direct Fido2 API only*: WebAuthn adapter rejects multiple entries and mismatched single allow credentials at `PreviewSignAdapter.cs:103-154`.
- Location at HEAD: `src/Fido2/src/Extensions/PreviewSign/PreviewSignAuthenticationInput.cs:17-49`; `src/Fido2/src/Extensions/Shared/ExtensionBuilder.cs:420-430`; `src/Fido2/src/Cbor/FidoSessionRequestEncoding.cs:75-83`.
- Spec / contract: “If the authenticator contains any credentials whose credential IDs appear as keys, the client selects one of them and sends the corresponding value to the authenticator as inputs to the signing algorithm.”; “Let signInputs be extSign.signByCredential[chosenCredentialIdB64].” — [Yubico draft sign extension v4](https://yubicolabs.github.io/webauthn-sign-extension/4/) §10.2.1. SDK contract: “Maps credential IDs to their corresponding signing parameters.” — `PreviewSignAuthenticationInput.cs:20-24`.
- Reference implementations: `python-fido2/fido2/ctap2/extensions.py:782-802` validates IDs against allow list and indexes `by_creds[websafe_encode(selected.id)]`; legacy .NET `GetAssertionParameters.cs:424-440` scopes signing input to a previously allowed credential rather than accepting an unsorted arbitrary map.
- Evidence: low-level builder calls `.First().Value` and `PreviewSignCbor.EncodeAuthenticationInput(signingParams)` with no credential-ID check, while assertion encoder separately serializes allow list. Insertion order of map changes submitted keyHandle/tbs; no credential match is required. WebAuthn layer blocks multi-credential selection deliberately, per `src/WebAuthn/CLAUDE.md:282-289`.
- Repro: `Fido2AuditReproTests.YESDK1634_MultiplePreviewSignCredentialsCannotSilentlySelectFirst` — FAILED as expected: expected NotSupportedException, no exception thrown. The correct behavior until preselection exists is to reject ambiguity.
- Remediation: bind selected credential ID to signing parameters at assertion request construction (including allow list), or reject multi-entry direct inputs when no selection context is available; never choose the first entry silently. API impact: additive selection argument or breaking rejection for currently accepted ambiguous maps. Proving test: multi-entry rejection and selected-ID-to-keyHandle encoding test. Depends on / interacts with: #26a uses similar credential preselection mechanism. Open decisions: implement probe-selection (recommend for complete spec behavior) versus explicit single-credential restriction (safe interim; recommend immediately).
