### #3 Direct CTAP largeBlob write input shape (YESDK-1611) - audit severity MED
- Verdict: CONFIRMED-WITH-CORRECTION | My severity: LOW for currently deployed YubiKeys; MED on authenticators advertising direct `largeBlob`.
- Location at HEAD: `src/Fido2/src/Extensions/LargeBlob/LargeBlobAssertionInput.cs:28-81`; `src/Fido2/src/Extensions/Shared/ExtensionBuilder.cs:93-110`. There is also a registration `LargeBlobInput` at `src/Fido2/src/Extensions/LargeBlob/LargeBlobInput.cs:32-75`; this is **not** the YubiKey `largeBlobKey` extension. Audit conflates the CTAP direct extension with the WebAuthn extension and storage protocol. No GetInfo gate exists on the direct builder; actual supported-extension lists on the connected devices were not measured.
- Spec / contract: “This extension is an alternative to the to authenticatorLargeBlobs command and the largeBlobKey extension for authenticators that can accept the full contents of a largeBlob in an authenticatorGetAssertion message. Authenticators MUST NOT support both extensions.” — CTAP 2.3 §12.4. “largeblob-inputs = { ? read : true ? write : bstr ? originalSize : uint }” and “If the input contains the read member and neither of write nor originalSize members, or contains the write and originalSize members but not the read member, then continue. Otherwise return CTAP2_ERR_INVALID_CBOR.” — CTAP 2.3 §12.4. This is **not** §12.3 `largeBlobKey`, whose assertion input is `"largeBlobKey": boolean` (§12.3). WebAuthn §10.1.5 `write` is opaque data; the compressed bytes and original size are the CTAP direct variant, not WebAuthn client input.
- Reference implementations: `python-fido2/fido2/ctap2/extensions.py:394-471` implements WebAuthn `largeBlob` over **largeBlobKey** plus `LargeBlobs`, not the CTAP direct extension; `blob.py:44-69,192-214` compresses for authenticatorLargeBlobs. `libfido2/src/largeblob.c:118-146` likewise uses per-credential array storage; this is not evidence that direct CTAP largeBlob is implemented by YubiKeys. The spec says authenticators MUST NOT advertise both.
- Evidence: `WithLargeBlobWrite(data)` creates a `LargeBlobAssertionInput { Write = data }`, `Encode()` emits a one-element map with `write` only; it neither compresses the data nor emits `originalSize`. `Read=true` plus Write can also encode a prohibited combination.
- Repro: `src/Fido2/tests/Yubico.YubiKit.Fido2.UnitTests/AuditV2/Fido2LargeBlobAuditReproTests.cs:20` `YESDK1611_DirectWriteCarriesOriginalSize` — FAILED as expected: expected map count 2, actual 1.
- Hardware repro: none: first establish that an authenticator advertises the **direct** `largeBlob` extension; GetInfo of currently connected YubiKeys was not queried and it would be misleading to test this using `largeBlobKey` devices.
- Remediation: for direct CTAP §12.4, compress `write` with DEFLATE and encode `originalSize` (uncompressed byte length), reject read/write mixtures; separate this type explicitly from `largeBlobKey` and restrict use to advertised extension. If direct extension is intentionally unsupported, remove its advertised builder surface or clearly document it as unsupported. API impact: additive `OriginalSize` / validated builder contract, potentially breaking invalid inputs. Proving test: `YESDK1611_DirectWriteCarriesOriginalSize`, plus a read/write rejection test. Depends on: #4 for unsigned direct-extension results. Open decision: implement direct §12.4 (recommended only if supporting a device that advertises it), or remove the misleading API and document YubiKey `largeBlobKey` + storage as the supported path.

### #4 Unsigned assertion extension outputs (YESDK-1612) - audit severity MED
- Verdict: CONFIRMED-WITH-CORRECTION | My severity: MED for direct-`largeBlob` devices, LOW for YubiKeys using `largeBlobKey`.
- Location at HEAD: `src/Fido2/src/Credentials/GetAssertionResponse.cs:87-111,130-197` drops key 0x08. In contrast, `src/Fido2/src/Credentials/MakeCredentialResponse.cs:79-106,188-204` already decodes makeCredential 0x06 into `UnsignedExtensionOutputs`; the audit should not imply both responses are missing it.
- Spec / contract: “unsignedExtensionOutputs (0x08) CBOR map of extension identifier → unsigned extension output values ... A map, keyed by extension identifiers, to unsigned outputs of extensions, if any.” — CTAP 2.3 §6.2 getAssertion response. “unsignedExtensionOutputs (0x06) CBOR map of extension identifier → unsigned extension output values” — CTAP 2.3 §6.1 makeCredential response. “Add an element to the unsigned extension outputs for this extension that conforms to largeblob-outputs ... and which contains a written member equal to the value of the written variable.” — CTAP 2.3 §12.4.
- Reference implementations: `python-fido2/fido2/ctap2/base.py:148-188` models top-level `unsigned_extension_outputs` on both attestation and assertion responses; its WebAuthn `largeBlobKey` adapter instead reads `response.large_blob_key` (`extensions.py:423-427,444-460`).
- Evidence: GetAssertionResponse extracts signed authenticator-data `ExtensionOutputs` only, switches on keys 1–7 and skips key 8; consequently a direct largeBlob `written` output cannot reach a caller.
- Repro: `src/Fido2/tests/Yubico.YubiKit.Fido2.UnitTests/AuditV2/Fido2LargeBlobAuditReproTests.cs:33` `YESDK1612_GetAssertionPreservesUnsignedLargeBlobOutput` — FAILED as expected: no `UnsignedExtensionOutputs` property. The synthesized key-8 response includes a true `largeBlob.written`.
- Remediation: capture key 8 as a dictionary of encoded values as makeCredential already does for key 6, retaining correct per-response key numbers; expose output safely and pass it to consumers. API impact: additive. Proving test: `YESDK1612_GetAssertionPreservesUnsignedLargeBlobOutput`. Depends on: #3 (direct `largeBlob` consumer). Open decisions: whether to expose raw encoded values alone or typed direct-largeBlob result as well; recommend raw plus typed parsing only where needed.

### #5 WebAuthn supported result drops largeBlobKey (YESDK-1613) - audit severity MED
- Verdict: CONFIRMED | My severity: MED (misreports successfully enabled feature).
- Location at HEAD: `src/Fido2/src/Credentials/MakeCredentialResponse.cs:185-187` decodes key 5; `src/WebAuthn/src/Client/WebAuthnClient.Registration.cs:359-364` passes only signed auth-data and unsigned output map; `src/WebAuthn/src/Extensions/ExtensionPipeline.cs:216-227` checks signed map; `src/WebAuthn/src/Extensions/Adapters/LargeBlobAdapter.cs:28-56` requests `largeBlobKey` yet searches for `largeBlobKey` in that signed map.
- Spec / contract: “Set the value of largeBlobKey (0x05) in the authenticatorMakeCredential response structure (i.e., not in the extensions field of the authenticator data) to the value of the generated largeBlobKey.” — CTAP 2.3 §12.3. “If an authenticator is selected and the selected authenticator supports large blobs, set supported to true, and false otherwise.” — WebAuthn L3 §10.1.5.
- Reference implementations: `python-fido2/fido2/ctap2/extensions.py:419-428` returns `supported=response.large_blob_key is not None`; `extensions.py:403-405` checks GetInfo's `largeBlobKey` extension and `largeBlobs` option together.
- Evidence: Fido2 response key 5 exists but is not an argument to `ParseRegistrationOutputs`; adapter checks the wrong map. MakeCredential key 6 unsigned outputs correctly supports the **alternative** CTAP direct `largeBlob` extension, not the returned `largeBlobKey`.
- Repro: `src/WebAuthn/tests/Yubico.YubiKit.WebAuthn.UnitTests/AuditV2/WebAuthnLargeBlobAuditReproTests.cs:15` `YESDK1613_LargeBlobKeyFromCtapResponseReportsSupported` — synthesizes and decodes makeCredential key 5, asserts key length 32; pipeline returns `Supported=false` and assertion FAILED as expected.
- Remediation: pass `ctapResponse.LargeBlobKey` (or a derived presence flag) through registration pipeline into adapter; optionally read direct-extension `largeBlob.supported` from unsigned map for direct-only devices, never from the signed `largeBlobKey` map. API impact: none if pipeline remains internal. Proving test: `YESDK1613_LargeBlobKeyFromCtapResponseReportsSupported`. Depends on: #4 if supporting the alternative direct extension during assertion; #13 for actual data interoperability. Open decision: policy when both advertised options and actual response disagree: recommend actual credential key presence for supported result.

### #12 Incorrect max fragment length (YESDK-1620) - audit severity MED
- Verdict: CONFIRMED | My severity: MED (device-dependent read/write failure).
- Location at HEAD: `src/Fido2/src/LargeBlobs/LargeBlobStorage.cs:74-103,271-315,341-350` defaults both constructors to 1024 and sends this as `get`; `src/Fido2/src/FidoSession.cs:155-157` reads GetInfo but does not retain `MaxMsgSize`. Existing integration callers `src/Fido2/tests/Yubico.YubiKit.Fido2.IntegrationTests/FidoLargeBlobTests.cs:118-125,214-224` do **not** supply fragment length. No shipping WebAuthn caller constructs LargeBlobStorage; the only explicit production constructor uses the default. Test callers can override the integer manually.
- Spec / contract: “A per-authenticator constant, maxFragmentLength, is here defined as the value of maxMsgSize (from the authenticatorGetInfo response) minus 64. ... If no maxMsgSize is given in the authenticatorGetInfo response) then it defaults to 1024, leaving maxFragmentLength to default to 960.” “If the value of get is greater than maxFragmentLength, return CTAP1_ERR_INVALID_LENGTH.” — CTAP 2.3 §6.10.2.
- Reference implementations: `python-fido2/fido2/ctap2/blob.py:100-110,122-129` derives `ctap.info.max_msg_size - 64` and uses it on reads; `libfido2/src/largeblob.c:440-458` calls `get_chunklen(dev)` before reading.
- Evidence: first default read sends `get=1024`, whereas absent maxMsgSize permits at most 960; explicit 1024 in an existing test is an intentional override, not validation of default.
- Repro: `src/Fido2/tests/Yubico.YubiKit.Fido2.UnitTests/AuditV2/Fido2LargeBlobAuditReproTests.cs:69` `YESDK1620_DefaultReadFragmentIs960Bytes` — FAILED as expected: expected 960, actual 1024.
- Remediation: compute fragment length from session/GetInfo before both reads and writes, default 960 only when info omits size; honor a documented explicit override only within device limits. API impact: may be additive session GetInfo or constructor changes; avoid requiring FidoSession implementation if IFidoSession.GetInfoAsync is available. Proving test: `YESDK1620_DefaultReadFragmentIs960Bytes` and a future GetInfo(maxMsgSize=2048) transport-level test expecting 1984. Depends on: #13 write interoperability. Open decision: cache GetInfo in FidoSession vs query via storage on creation; recommend querying session via existing GetInfoAsync and retaining calculated limit per storage instance.

### #13 Incompatible per-credential array entries (YESDK-1621) - audit severity MED
- Verdict: CONFIRMED | My severity: HIGH interoperability / data availability (not evidence of cryptographic plaintext disclosure).
- Location at HEAD: `src/Fido2/src/LargeBlobs/LargeBlobData.cs:20-30,57-85,95-175,206-269`; `src/Fido2/src/LargeBlobs/LargeBlobStorage.cs:186-216` creates entries and serializes array. Audit accurately identifies private format.
- Spec / contract: “The elements of the large-blob array MUST conform to the following large-blob map structure.” “ciphertext (0x01) Byte String Required ... authentication tag at the end”; “nonce (0x02) Byte String Required ... exactly 12 bytes long”; “origSize (0x03) Unsigned Integer Required ... length, in bytes, of the uncompressed data.” “Plaintext: the compressed opaque large-blob data. Associated data: The value 0x626c6f62 ("blob") || uint64LittleEndian(origSize).” — CTAP 2.3 §6.10.3. “Let plaintext equal origData after compression with DEFLATE.” — CTAP 2.3 §6.10.5. “Platforms MUST ensure that the large-blob array ... is a CBOR array where all entries conform to the large-blob map structure defined below.” — CTAP 2.3 §6.10.2.
- Reference implementations: `python-fido2/fido2/ctap2/blob.py:44-69` raw DEFLATE (`wbits=-zlib.MAX_WBITS`), AAD `b"blob" + struct.pack("<Q", orig_size)`, AES-GCM and map `{1:ct||tag,2:nonce,3:origSize}`; `:72-79,117-145,176-214` unpacks array and reads/writes. `libfido2/src/largeblob.c:50-82,118-146,277-352,358-393` corroborates AAD, compression and CBOR map.
- Evidence: SDK plaintext is private CBOR `{h'': h'data'}` (not DEFLATE), AES-GCM AAD omitted, array items single byte strings holding nonce||ciphertext||tag rather than maps. `Deserialize()` attempts ReadByteString against a conforming map and fails; spec decoders reject SDK array entries. The raw array SHA-256 trailer itself is correctly constructed.
- Repro: `src/Fido2/tests/Yubico.YubiKit.Fido2.UnitTests/AuditV2/Fido2LargeBlobAuditReproTests.cs:88` `YESDK1621_ReadsPythonFido2CompatibleArray` builds a conforming array in C# using raw `DeflateStream`, AES-GCM with spec AAD, canonical CBOR and SHA-256 suffix: FAILED as expected: ReadByteString encounters CBOR major type 5 (map). `:98` `YESDK1621_SdkWrittenArrayIsSpecDecodable`: FAILED as expected: ReadStartMap encounters major type 2 (byte string). Python dependencies not installed (`ModuleNotFoundError: No module named 'cryptography'`), so no actual python-produced vector was generated locally; the C# generator follows the inspected reference algorithm, not a literal known-good python byte vector.
- Hardware repro: `src/Fido2/tests/Yubico.YubiKit.Fido2.IntegrationTests/AuditV2/Fido2LargeBlobAuditReproTests.cs:20` `YESDK1621_SdkWriteIsReadablePerSpec` — needs PIN + touch; writes SDK entry and parses actual raw authenticator array as spec (not run). `:113` `YESDK1621_ReadsPythonFido2WrittenBlob` — after a user writes a blob with `C-interop.py`, reads with SDK; needs manual PIN + UP to acquire the same key in advance, though the SDK read alone does not touch. Do not run both on the same credential without deliberately sequencing them, as writes replace its prior blob. The first test assumes the array fits in one fragment and cleans test RP credentials, not pre-existing blobs.
- Remediation: rewrite LargeBlobEntry/Array to match map fields 1,2,3, raw DEFLATE, AAD and proper authenticated decrypt/decompression/origSize validation; preserve valid unrelated entries and skip malformed maps. API impact: potentially breaking shape of public `EncryptedData` if changed to modeled fields; choose a migration appropriate for pre-release. Proving tests: both `YESDK1621_*` unit tests and hardware tests. Depends on: #12 safe fragment size, #14 corrupt array fallback, #16 temporary plaintext cleanup. Open decisions: existing private-format data migration (recommend explicit one-time import only if an external persisted deployment needs it; otherwise no compatibility shim), and decompression maximum (CTAP §6.10.4 recommends at least 1 MiB).

### #14 Bad array checksum response (YESDK-1622) - audit severity MED
- Verdict: CONFIRMED | My severity: MED (loss of availability after torn/corrupt write).
- Location at HEAD: `src/Fido2/src/LargeBlobs/LargeBlobData.cs:206-224` throws on checksum mismatch; `src/Fido2/src/LargeBlobs/LargeBlobStorage.cs:113-123` passes exception through.
- Spec / contract: “Once complete, the platform MUST confirm that the embedded SHA-256 hash is correct ... If not, the configuration is corrupt and the platform MUST discard it and act as if the initial serialized large-blob array was received.” — CTAP 2.3 §6.10.2. Initial bytes defined at §6.10: “h’8076be8b528d0075f7aae98d6fa57a6d3c'”.
- Reference implementations: `python-fido2/fido2/ctap2/blob.py:117-134` returns [] on mismatch; `libfido2/src/largeblob.c:413-463` substitutes a zero-length CBOR array on bad digest.
- Evidence: hash comparison detects corruption but `ReadLargeBlobArrayAsync` does not recover; distinct from malformed *valid-checksum* CBOR, which deserves separate validation policy.
- Repro: `src/Fido2/tests/Yubico.YubiKit.Fido2.UnitTests/AuditV2/Fido2LargeBlobAuditReproTests.cs:125` `YESDK1622_CorruptChecksumActsAsInitialArray` — FAILED as expected: `ArgumentException: Large blob array hash verification failed`.
- Remediation: on checksum mismatch during storage read, discard and return initial empty array; preserve strict failures for transport faults and separately validate malformed CBOR. API impact: none, behavioral recovery. Proving test: `YESDK1622_CorruptChecksumActsAsInitialArray`. Depends on: #13 array representation. Open decisions: whether to implement fallback at storage read only (recommended; retain a strict Deserialize for explicit direct callers) or alter Deserialize contract.

### #16 Temporary plaintext retention (YESDK-1624) - audit severity MED
- Verdict: CONFIRMED-WITH-CORRECTION | My severity: LOW/MED, conditional local heap-dump exposure, not a remote read.
- Location at HEAD: `src/Fido2/src/LargeBlobs/LargeBlobData.cs:74-85,102-133,136-175`; `src/Fido2/src/LargeBlobs/LargeBlobStorage.cs:199-216,240-265`. Exact number of copies varies by parser internals; `plaintext.ToArray()` and `reader.ReadByteString()` definitely allocate separately. Current `TryDecrypt()` never zeroes the decrypted plaintext; `Encrypt()` never zeroes created CBOR plaintext. `SetBlobAsync` and `DeleteBlobAsync` throw away the returned data after match checks.
- Spec / contract: repository `CLAUDE.md:58-60`: “✅ ALWAYS zero sensitive data: `CryptographicOperations.ZeroMemory()`”; “✅ Classify byte data by semantic meaning, not by direction. ... YubiKey-returned authentication material, token material, decrypted plaintext, or secret-derived output does.” Module `src/Fido2/CLAUDE.md:323-339` also demands zeroing sensitive crypto buffers. This is a repo memory-hygiene contract, not a CTAP wire requirement.
- Reference implementations: `libfido2/src/largeblob.c:118-153` frees plaintext via its blob cleanup path after sealing, whereas SDK leaves created `byte[]` unzeroed; C native cleanup and managed GC differ. `python-fido2/fido2/ctap2/blob.py:72-79,176-211` uses immutable Python `bytes` without a comparable zeroing guarantee, so Python is *not* a model for this .NET security rule.
- Evidence: successfully decrypted data remains in the local `plaintext` after `ParseDecryptedBlob()` returns; copied CBOR input and extracted value are not cleared on replacement/delete; even a wrong-key attempt allocates a plaintext buffer before `CryptographicException`. Memory disclosure additionally requires sensitive content plus access to process memory/crash dump. Caller-owned data returned by `GetBlobAsync` cannot be zeroed before returning; document caller responsibility separately.
- Repro: `src/Fido2/tests/Yubico.YubiKit.Fido2.UnitTests/AuditV2/Fido2LargeBlobAuditReproTests.cs:146` `YESDK1624_DecryptedTemporaryPlaintextIsCleared` — FAILED as expected: 6/6 bytes of parser's temporary plaintext remain nonzero. This internal-method probe pins current implementation and should be adjusted when refactoring the parser; it does not directly observe GC-discarded copies.
- Remediation: finally-zero owned temporary decrypt/encrypt buffers on both success and failure; avoid extra `ToArray()` when possible, clear any owned parser copy and discarded match output; preserve only explicitly returned caller-owned result. On #13 rewrite use a single temporary compressed/decompressed buffer with well-defined ownership and finally blocks. API impact: none. Proving test: `YESDK1624_DecryptedTemporaryPlaintextIsCleared`, plus instrumentation for encrypt and discard branches following format rewrite. Depends on: #13 (new wire format should incorporate cleanup). Open decisions: returned plaintext ownership contract (recommend explicit docs advising caller to zero returned `byte[]`).
