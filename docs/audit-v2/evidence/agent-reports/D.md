# Agent D — Fido2 CTAP request encoders

### #10 makeCredential accepts forbidden `options.up=false` (YESDK-1618) - audit severity MED
- Verdict: CONFIRMED | My severity: MED (invalid low-level request, not a bypass; no evidence the SDK's own WebAuthn registration emits it).
- Location at HEAD: `src/Fido2/src/Credentials/MakeCredentialOptions.cs:51-57` exposes nullable `UserPresence`, with misleading XML documentation saying false is "rarely allowed". `src/Fido2/src/Cbor/FidoSessionRequestEncoding.cs:23-49,100-124` emits integer parameter 7 containing text key `"up"` and Boolean false if explicitly set. `src/Fido2/src/FidoSession.cs:229-279` accepts the public option and sends the encoded command unchanged. HEAD location; audit referenced the same encoder block, with no material drift.
- Spec / contract: "Platforms MAY send the \"up\" option key to CTAP2.1 authenticators, and its value MUST be true if present. The value false will cause a CTAP2_ERR_INVALID_OPTION response regardless of authenticator version." — CTAP 2.3 §6.1, authenticatorMakeCredential option keys (`ctap23.txt:743-746`). Algorithm §6.1.2 additionally says: "If the \"up\" option is false, end the operation by returning CTAP2_ERR_INVALID_OPTION." (`ctap23.txt:933-935`). CTAP2.0 compatibility note: "FIDO_2_0 (aka CTAP2.0) authenticators will return a CTAP2_ERR_INVALID_OPTION response if \"up\" is present. Platforms SHOULD NOT send \"up\" to a CTAP2.0 authenticator." (§6.1, `ctap23.txt:764`).
- Reference implementations: `python-fido2/fido2/ctap2/base.py:376-427,52-59` accepts an arbitrary `options` mapping for its raw `Ctap2.make_credential` and omits only top-level `None` values; it does **not** reject a caller-provided `{"up": False}`. Its high-level registration chooses only `rk` and `uv`, never `up` (`fido2/client/__init__.py:833-865`). Its legacy selection fallback sends a dummy makeCredential with `pin_uv_param=b""`, not `up=false` (`fido2/client/__init__.py:618-631`); CTAP 2.3 §6.1.2 explicitly describes the zero-length `pinUvAuthParam` selection operation (`ctap23.txt:872-884`) and provides no exception for `up=false`. `libfido2/src/cred.c:53-105` uses `cbor_encode_cred_opt(rk,uv)` for makeCred; `libfido2/src/cbor.c:764-777` encodes only `rk` and `uv`, never `up`. Its getAssertion option encoder *does* handle `up` (`cbor.c:779-792`).
- Evidence: The new CBOR repro passes `UserPresence=false, ResidentKey=true` and encounters literal `"up": false` under key 7. Existing `src/Fido2/tests/Yubico.YubiKit.Fido2.UnitTests/Cbor/FidoSessionRequestEncodingTests.cs:53-97` actually expects this invalid value. `src/WebAuthn/src/Client/WebAuthnBackend.cs:115-126,148-154` constructs makeCredential options without assigning `UserPresence`, so the WebAuthn layer does not send `up=false` in this flow. In contrast, `src/Fido2/src/Cbor/FidoSessionRequestEncoding.cs:135-159` intentionally serializes getAssertion `up=false`, and `src/WebAuthn/src/Internal/ExcludeListPreflight.cs:114-125` uses it for exclude-list probing. CTAP 2.3 §5.9 says: "In order to determine whether authenticatorMakeCredential’s excludeList or authenticatorGetAssertion’s allowList contain credential IDs that are already present on an authenticator, a platform typically invokes authenticatorGetAssertion with the \"up\" option key set to false and optionally pinUvAuthParam one or more times." (`ctap23.txt:572`); §6.2 also notes `options.up` "may be set to false in CTAP \"pre-flight\" commands" (`ctap23.txt:1402`).
- Repro: `src/Fido2/tests/Yubico.YubiKit.Fido2.UnitTests/AuditV2/Fido2AuditReproTests.cs:26` — `YESDK1618_MakeCredentialDoesNotEncodeFalseUserPresence` FAILED as expected: `Assert.NotEqual() Failure: Strings are equal; Expected: Not "up"; Actual: "up"`. `:64` — `YESDK1618_GetAssertionStillEncodesFalseUserPresence` succeeded and guards the allowed getAssertion preflight path. Unit tests assert the **correct** encoding, not current behavior.
- Hardware repro: `src/Fido2/tests/Yubico.YubiKit.Fido2.IntegrationTests/AuditV2/Fido2AuditReproTests.cs:29` — `YESDK1618_MakeCredentialFalseUserPresenceReturnsInvalidOption`: expects status `0x2C`/`InvalidOption` from the public low-level session; built, **not run**. Needs touch? **No anticipated touch**: options are processed before user presence in CTAP §6.1.2 (`ctap23.txt:908-937`); no PIN entry or setup is performed. No `RequiresUserPresence` trait because the request should fail before touch; if device firmware asks for PIN or touch earlier despite the normative processing order, orchestration needs human coordination. Command: `dotnet toolchain.cs -- test --integration --project Fido2 --filter "FullyQualifiedName~YESDK1618_MakeCredentialFalseUserPresenceReturnsInvalidOption"` (human/orchestrator only). Note this hardware characterization test deliberately checks the explicit invalid raw call; it may require revision if the eventual SDK fix rejects or normalizes false before transmission.
- Remediation: In `FidoSessionRequestEncoding.WriteMakeCredentialOptions` and `HasMakeCredentialOptions`, **never emit `"up":false`**. Recommend reject explicit `MakeCredentialOptions.UserPresence=false` with `ArgumentException` at the public `FidoSession.MakeCredentialAsync` input boundary rather than silently interpreting an explicit attempt to disable consent as a default requiring consent; if adopting rejection, change the CBOR repro to assert rejection at the session boundary and add a valid `up` serialization test. Alternatively omit false with explicit documentation that omission means **true**; this makes the current CBOR repro pass but changes caller intent silently. On CTAP2.0, omit even explicit true if authenticator version can be determined reliably. Update misleading XML documentation and the existing `WithAllOptions` unit expectation. **Do not change getAssertion encoding**.
- API impact: Behavioral breaking for callers explicitly sending makeCredential `UserPresence=false`; no signature change for rejection or omission. Signature change only if removing the property (not recommended while getAssertion uses its own property).
- Proving test: `YESDK1618_MakeCredentialDoesNotEncodeFalseUserPresence` (or the recommended rejection variant) and `YESDK1618_GetAssertionStillEncodesFalseUserPresence`; hardware status test characterizes pre-fix wire behavior only.
- Depends on / interacts with: #2/#7 (WebAuthn option default mapping; separately owned by agent A); the WebAuthn registration path currently leaves `up` null. Do not conflate getAssertion's `up=false` with this fix.
- Open decisions: Reject explicit false (recommended; prevents false impression of silent credential creation) or omit it (silent behavior change). Also decide whether to omit explicit true for CTAP2.0 authenticators.

### NEW duplicate `pubKeyCredParams` allowed into makeCredential (NEW-FIDO2-DUPLICATE-ALGORITHMS) - audit severity not rated
- Verdict: CONFIRMED | My severity: LOW (invalid platform request; authenticator may tolerate duplicates).
- Location at HEAD: `src/Fido2/src/FidoSession.cs:250-255` rejects only an empty list; `src/Fido2/src/Cbor/FidoSessionRequestEncoding.cs:30-34,162-174` serializes every credential parameter unchanged into key 4.
- Spec / contract: "The array is ordered from most preferred to least preferred and MUST NOT include duplicate entries." — CTAP 2.3 §6.1, `pubKeyCredParams (0x04)` (`ctap23.txt:678-681`).
- Reference implementations: `python-fido2/fido2/ctap2/base.py:376-424` forwards the caller's key_params list into the request; `fido2/client/__init__.py:858-865` forwards `_cbor_list(key_params)` without deduplication here. `libfido2/src/cred.c:65-69` uses a single configured `cred->type` through `cbor_encode_pubkey_param`, so this particular duplication cannot arise there.
- Evidence: Passing the *same* `PublicKeyCredentialParameters(ES256)` instance twice produces a key-4 CBOR array of length 2. This is separate from #10, #2, and #7.
- Repro: `src/Fido2/tests/Yubico.YubiKit.Fido2.UnitTests/AuditV2/Fido2AuditReproTests.cs:92` — `NEW_MakeCredentialDoesNotEncodeDuplicateCredentialParameters` FAILED as expected: `Assert.Equal() Failure: Values differ; Expected: 1; Actual: 2`.
- Hardware repro: none; encoded CBOR suffices.
- Remediation: At `FidoSession.MakeCredentialAsync`, validate or deduplicate by `(Type, Algorithm)` while preserving first-occurrence preference order. Prefer rejecting duplicate entries explicitly, rather than silently changing caller input. Public API impact: behavioral breaking for duplicate-list callers, no signature change. Proving test: `NEW_MakeCredentialDoesNotEncodeDuplicateCredentialParameters` if deduplication is selected; adapt to assert rejection before sending if validation is selected. Depends on / interacts with: none. Open decision: reject (recommended) vs stable deduplication.

### Supporting evidence for #2 / sweep scope (no #2/#7 tests)
- `src/WebAuthn/src/Client/WebAuthnBackend.cs:124-125` assigns `ResidentKey = request.Options?.TryGetValue("rk", out var rk) == true && rk` and similarly for `UserVerification`. Absent dictionary entries become **non-null false**, not null. `src/Fido2/src/Cbor/FidoSessionRequestEncoding.cs:100-129` checks `HasValue` and writes `"rk":false` and `"uv":false`; only *actual nulls* are omitted. `src/WebAuthn/src/Client/WebAuthnBackend.cs:180-189` preserves getAssertion option absence by assigning only if present.
- Swept `FidoSessionRequestEncoding.cs:23-159`, `Pin/ClientPin.cs` request construction, `CredentialManagement/CredentialManagement.cs:254-403`, and `Config/AuthenticatorConfig.cs:176-280`. Empty makeCredential `excludeList` and getAssertion `allowList` are omitted by the `Count > 0` checks at `FidoSessionRequestEncoding.cs:36-39,75-78`, satisfying CTAP 2.3 §6.1 "If this parameter is present, it MUST NOT be empty" (`ctap23.txt:683-688`) and §6.2 "A platform MUST NOT send an empty allowList—if it would be empty it MUST be omitted" (`ctap23.txt:1320-1325`). `pinUvAuthProtocol` accompanies nonempty `pinUvAuthParam` at `FidoSessionRequestEncoding.cs:51-56,90-95`; config/credMgmt commands send both protocol and auth parameter. The `uv`+`pinUvAuthParam` combination is *also* reachable through the public low-level options and the WebAuthn mapping; CTAP 2.3 §6.1 states "Platforms MUST NOT include both the \"uv\" option key and the pinUvAuthParam parameter in the same request" (`ctap23.txt:760`), and §6.2 likewise (`ctap23.txt:1375`). **Do not classify this as a separate new finding here:** it overlaps agent A's #2 option mapping; no #2/#7 test was written. Nothing else in the swept encoders was established as a distinct CTAP 2.3 MUST violation from the inspected paths. The default protocol `2` when a nonempty auth param has no protocol is not intrinsically invalid if supported but may be unsupported on a particular device; zero-length auth params have intentional selection semantics in §6.1.2/§6.2.2, so their omission warrants separate design review rather than claiming a proven MUST violation.
