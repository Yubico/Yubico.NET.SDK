### #17 Private-key intermediate copies (YESDK-1625) — audit severity MED
- Verdict: **PARTIAL** (most SDK copies already fixed at audited commit 65e36386) | My severity: LOW for remaining managed BCL copy; local-memory disclosure prerequisite.
- Location at HEAD: `src/Core/src/Cryptography/AsnPrivateKeyDecoder.cs:347-374`, `RSAParametersExtensions.cs:60-100`, `RSAPrivateKey.cs:114-131`, `ECPrivateKey.cs:120-132,174-183,223-247`. Audit line numbers before 65e36386 are obsolete.
- Spec / contract: “A new disposable private-key object that owns its decoded key material.” — `AsnPrivateKeyDecoder.cs:37-39`; “ALWAYS zero sensitive data: `CryptographicOperations.ZeroMemory()`” — root `CLAUDE.md:58-65`. No protocol specification governs host heap hygiene.
- Reference implementations: Runtime v10.0.0 [`EccSecurityTransforms.macOS.cs`, `ExtractPublicKeyFromPrivateKey`](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/Common/src/System/Security/Cryptography/EccSecurityTransforms.macOS.cs): `ReadEncryptedPkcs8(..., out ecParameters)` **overwrites** the `ref ECParameters` holding the original private D after reimporting the temporary key, without clearing the original D. [`EccKeyFormatHelper.cs`, `FromECPrivateKey`](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.Security.Cryptography/src/System/Security/Cryptography/EccKeyFormatHelper.cs) allocates `D = key.PrivateKey.ToArray()`. [`EccSecurityTransforms.cs`, `ImportParameters`/`ImportKey`](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/Common/src/System/Security/Cryptography/EccSecurityTransforms.cs) invokes that derivation when Q is absent, but its pooled encoded import buffer **is** cleared via `CryptoPool.Return`. The abandoned D copy belongs to the runtime, not to the SDK. BCL = base class library.
- Evidence: RSA decoder's first private arrays are zeroed in `finally`, normalization clears arrays replaced by padding and clears on failure, RSA wrapper clears decoded normalized parameters after copying; EC PKCS#8 decoder's D and ECDH export D are zeroed after copying. `CreateFromValue` zeroes both SDK-generated temporary D arrays and disposes `ECDsa`; existing `PrivateKeyDecodingZeroingTests` covers these cases. Residual on macOS is caused by `ECDsa.Create(parameters)` at `ECPrivateKey.cs:232` with D-only parameters. **No PIV or SecurityDomain production import path invokes `ECPrivateKey.CreateFromValue`:** search `src/Piv/src` and `src/SecurityDomain/src` found only public-key `CreateFromValue` uses (`PivKeyProtocol.cs:497`, `SecurityDomainSession.cs:616`); PIV imports a caller-supplied `IPrivateKey` (`IPivSession.cs:197-211`), SecurityDomain tests construct via `CreateFromParameters`. Direct public calls to the Core `ECPrivateKey.CreateFromValue` factory remain affected. Do not mislabel public-key calls as private-key import sites.
- Repro: code inspection for BCL-only copy (cannot spy on inaccessible runtime array). Existing `PrivateKeyDecodingZeroingTests` run: total 12, failed 0. A managed heap assertion on the hidden BCL temporary is not a reliable unit test.
- Remediation: replace D-only `ECDsa.Create(parameters)` with a derivation that does not discard a managed secret (e.g. vetted native/crypto routine or obtain Q via an API whose managed intermediates are known to clear); `CreateFromParameters` only works when the caller **already supplies correct Q**, so it is not itself a D→Q workaround. Optionally report the BCL copy upstream with a focused macOS repro. No SDK remediation needed for fixed RSA/PKCS#8 paths.
- API impact: none if factory internals change. Proving test: existing 12 private-array zeroing tests plus platform-specific heap instrumentation for runtime internals, not a false-positive ordinary unit test. Depends on / interacts with: #27 (do not trust caller-provided Q). Open decisions: native derivation vs accepting/documenting the runtime-local residual; recommend investigate upstream first.

### #22 PIV cross-connection PIN status (YESDK-1630) — audit severity MED
- Verdict: **CONFIRMED-WITH-CORRECTION** for connection/disposition and threat mechanism; reported cross-process hardware exploit **not independently run here** | My severity: MED, contingent on other processes accessing the same reader and PIN=ONCE.
- Location at HEAD: `src/Core/src/Transports/SmartCard/UsbSmartCardConnection.cs:125-138,198-224,301-303`, `src/Core/src/Native/Desktop/SCard/SCardCardHandle.cs:35-38`, `src/Core/src/CoreCompatSwitches.cs:21-27`, `src/Piv/src/PivSession.cs:386-390`.
- Spec / contract: “**SCARD_LEAVE_CARD** — Do not do anything special.”; “**SCARD_RESET_CARD** — Reset the card.”; “**SCARD_UNPOWER_CARD** — Power down the card.” — [Microsoft `SCardDisconnect`, `dwDisposition`](https://learn.microsoft.com/en-us/windows/win32/api/winscard/nf-winscard-scarddisconnect). “A security status indicator is said to be an application security status indicator if it is set to FALSE when the currently selected application changes from one application to another.” and “The security status indicators associated with the PIV Card Application PIN ... are application security status indicators” — [NIST SP 800-73-5 Part 2 §2.4.2](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-73pt2-5.pdf). This does **not** say that disposing a host connection deselects the applet or resets the card. “Once the correct PIN has been provided, multiple private key operations may be performed without additional cardholder consent.” — [YubiKey technical manual, PIV slot 9A](https://docs.yubico.com/hardware/yubikey/yk-tech-manual/yk5-apps-piv.html).
- Reference implementations: Legacy .NET SDK `Yubico.Core/src/Yubico/Core/Devices/SmartCard/DesktopSmartCardDevice.cs:134-147` defaults shared with identical exclusive AppContext switch; `Yubico.Core/src/Yubico/PlatformInterop/Desktop/SCard/SCardCardHandle.cs:27,42-43` defaults **RESET_CARD** on disconnect (different from v2). `yubikey-manager/ykman/pcsc/__init__.py:130-149` tries pyscard `ExclusiveConnectCardConnection` then falls back to shared; `:77-93` calls pyscard `connection.connect()` and `disconnect()` without explicit disposition; pyscard's actual disconnect disposition is dependency-specific and not asserted here. Android desktop `desktop/.../PcscDevice.java:59` uses `terminal.connect("T=1")`, `PcscSmartCardConnection.java:41-43,65-70` acquires/releases Java exclusive transaction and `card.disconnect(true)` (reset). Android mobile uses direct USB/NFC transports, not desktop PC/SC (`android/.../NfcYubiKeyDevice.java:64-69`). Swift `USBSmartCardConnection.swift:223-259` uses CryptoTokenKit `makeSmartCard` / `beginSession` / `endSession`; no explicit PC/SC share/disposition option in this path.
- Evidence: `SCARD_SHARE.SHARED` default; actual compatibility switch `CoreCompatSwitches.OpenSmartCardHandlesExclusively` **does exist**, set before opening handles to request `EXCLUSIVE`. Its existence is a correction to any claim it is absent. Card handle defaults `LEAVE_CARD`; disposal ends transactions with `LEAVE_CARD` and disconnects through safe handle. Core device lease is in-process only (`src/Core/CLAUDE.md:432-440`). PIN verification sets applet state, not SDK-handle identity. `SELECT PIV` on every new session may or may not change this state on actual hardware: the audit reports that it did not on one 5.7.4 device; needs independent hardware confirmation.
- Repro: hardware-only `src/Piv/tests/Yubico.YubiKit.Piv.IntegrationTests/AuditV2/PivAuditHardwareReproTests.cs:26`, `YESDK1630_PinOnceStateSurvivesConnectionDisposal`: reset, configure PIN=ONCE/TOUCH=NEVER, baseline no-PIN attempt requires 6982 (SDK surfaces as `InvalidOperationException`), verify PIN on another handle, dispose, sign without PIN on third independent handle and verify signature. **In-process separate native connections**, not child process; this approximates the cross-process mechanism and is explicitly weaker. RequiresHardware only; no user touch or manual PIN entry. **Written and built, NOT RUN.** Command: `dotnet toolchain.cs -- test --integration --project Piv --filter "FullyQualifiedName~YESDK1630_PinOnceStateSurvivesConnectionDisposal"` (runs module unit tests too only if filter matches; integration selection is controlled by `--integration`).
- Remediation: decide security/lifetime policy with owners: document that PIN=ONCE status is card-wide; prefer an opt-in **sensitive-session** reset or explicit exclusive+reset mode where threat model requires it. Exclusive alone cannot erase status after the handle closes; reset alone with shared readers disrupts gpg-agent, browsers, and operating-system smart-card consumers, killing their card state. A blanket RESET_CARD or exclusive default is not a harmless compatibility change. Handle failure to acquire exclusive explicitly.
- API impact: additive for per-connection/per-session disposition policy; breaking if defaults change. Proving test: cross-process child connection with independent PC/SC context, baseline 6982 then 9000 then check opt-in reset blocks; included in-process precursor. Depends on / interacts with: session ownership and other applications' state. Open decisions: recommend opt-in secure isolation with explicit disruption warning, not global default reset; coordinate threat model and coexistence requirements.

### #24 Ed25519 signs altered message (YESDK-1632) — audit severity MED/HIGH
- Verdict: **CONFIRMED** | My severity: HIGH for silent incorrect signatures/input collisions, subject to supported message length.
- Location at HEAD: `src/Piv/src/PivSession.cs:486-528,821`, `src/Piv/src/Cryptography/PivCryptographicOperations.cs:77-110,394-447`; `IPivSession.cs:247-266,275-300`.
- Spec / contract: “The inputs to the signing procedure is the private key, a 32-octet string, and a message M of arbitrary size.” — [RFC 8032 §5.1.6](https://www.rfc-editor.org/rfc/rfc8032#section-5.1.6). SDK: “EdDSA: Sign message directly” — `IPivSession.cs:255`. YubiKey firmware 5.7 introduces Ed25519 PIV algorithm `0xE0` ([YubiKey PIV introduction](https://developers.yubico.com/PIV/Introduction/YubiKey_and_PIV.html)); no official source found that states exact maximum Ed25519 GENERAL AUTHENTICATE message length. APDU/transport limits may cap actual accepted message length; reject oversized explicitly, never truncate. Tests use 10 and 64 bytes only.
- Reference implementations: `yubikey-manager/yubikit/piv.py:546-549,1135-1160`: `_pad_message` returns Ed25519 message unchanged, `sign()` passes it to `_use_private_key`. `yubikit-android/piv/.../PivSession.java:395-416` forwards Ed25519 payload unchanged; Swift PIV signing does not implement this .NET formatting function. Existing SDK hardware test `PivCryptoTests.cs:101-129` only asserts 64-byte signature, **not** verification against original message.
- Evidence: both overloads reach `PrepareDataForCrypto`; Ed25519 is hard-coded to 32 (`:404`), oversized message takes first 32 (`:436-440`), shorter is right-padded (`:442-446`). Message contents, not signature width, are modified before TLV 0x81 is sent.
- Repro: `src/Piv/tests/Yubico.YubiKit.Piv.UnitTests/AuditV2/PivAuditReproTests.cs:11-35`, `YESDK1632_Ed25519ChallengeContainsEntireMessage(10/64)` uses real PIV session + RecordingSmartCardConnection and compares entire APDU. Both **FAILED as expected**, expected APDU lengths 16/70 versus actual 38. Hardware `PivAuditHardwareReproTests.cs:69-94`, `YESDK1632_Ed25519SignsUnmodifiedShortAndLongMessages`, PIN=ONCE/TOUCH=NEVER, OpenSSL 3 `pkeyutl -verify -rawin` independent verification against original 10/64-byte messages; **built, NOT RUN**; requires OpenSSL executable on PATH. Command: `dotnet toolchain.cs -- test --integration --project Piv --filter "FullyQualifiedName~YESDK1632_Ed25519SignsUnmodifiedShortAndLongMessages"`.
- Remediation: branch Ed25519 before ECC digest sizing; forward original message into TLV 0x81 unchanged, enforce a documented device/transport maximum and fail explicitly beyond it. Keep zeroing owned copied payload. API impact: none for accepted lengths; changing previously returned incorrect signature is intended behavior correction. Proving tests: both APDU unit cases plus hardware OpenSSL verifier. Depends on / interacts with: #26b shares sizing function. Open decisions: determine exact per-firmware message cap via protocol/device spec + controlled hardware; do not infer arbitrary unlimited APDU payload from RFC 8032.

- Verdict: **PARTIAL** (PIV subitems both present; other modules' #26 subitems out of this assignment) | My severity: HIGH for retry reset where callers assume old PIN remains; MED for cryptographic input alteration.
- Location at HEAD: `src/Piv/src/IPivSession.cs:158-164`, `PivSession.cs:426-430`, `Metadata/PivMetadataProtocol.cs:433-472`; `Cryptography/PivCryptographicOperations.cs:394-448`.
- Spec / contract: “Both PIN and PUK will be reset to default values when this is executed.” — [Yubico PIV extensions, `SET PIN RETRIES`](https://developers.yubico.com/PIV/Introduction/Yubico_extensions.html) (lines 236-238; command section, not numbered); [Yubico PIV commands, `Set PIN retries`](https://docs.yubico.com/yesdk/users-manual/application-piv/commands.html#set-pin-retries) repeats the warning. “2. Yubico PIV commands `Authenticate: sign` says “If the key is EccP256, the digest must be 256 bits (32 bytes) or shorter”; it does not authorize appending zero bytes to the right.
- Reference implementations: `yubikey-manager/yubikit/piv.py:1046-1059` warns in public docstring both PIN and PUK reset; `:546-559` right-justifies short EC digest **but appears to use `byte_len // 8` rather than `byte_len` (likely reference bug: `rjust(4)` for P-256 and `rjust(6)` for P-384); do not treat it as full-width padding oracle**. Legacy .NET SDK v1 `Piv/Commands/AuthenticateSignCommand.cs:194-244` instructs prepending 00 for short EC digests and requires proper RSA block length; explicit-algorithm constructor delegates raw data without silent truncation.
- Evidence: `SetPinAttemptsAsync` contract only says “Set PIN and PUK retry limits”, code sends `00 FA pinAttempts pukAttempts` without any warning to caller; internal remark at `PivMetadataProtocol.cs:437` knows reset side effect. Protocol says PIN verification also required, while v2 `:449-466` checks management authentication only and does not verify PIN itself (whether card enforces it on given firmware not independently tested). `PrepareDataForCrypto`: short EC `span.CopyTo(padded)` at 445 **appends** zeroes; 2-byte `A1 B2` becomes `A1 B2 00 ...` rather than `00 ... A1 B2`; oversized RSA `span.Slice(span.Length - expectedLength)` loses leading bytes, potentially mapping distinct requests to same private operation. Leftmost truncation of long EC digests at `:436-440` agrees with FIPS for byte-aligned curves.
- Repro: `PivAuditReproTests.cs:38-52`, `YESDK1634_ShortEcDigestIsLeftPaddedNotRightPadded` **FAILED as expected** (wanted 30 zeroes first, got `[161,178,0,...]`); `:55-65`, `YESDK1634_OversizedRsaBlockIsRejectedRatherThanSilentlyTruncated` **FAILED as expected**, no `ArgumentException`. Retry-reset subitem is doc/API-only and needs a hardware test to show secret reset; no fake test claims to simulate on-device credential state.
- Remediation: add explicit XML warning to `IPivSession.SetPinAttemptsAsync` and facade, optionally rename high-level operation / require explicit acknowledgment with a new API or provide an atomic convenience flow that immediately changes both secrets (requires carefully defined failure/recovery behavior; never imply atomicity of distinct commands). For sizing: right-align short EC digest if accepting it, otherwise reject noncanonical lengths, and reject oversized RSA before sending any APDU. API impact: documentation additive; required acknowledgment/rename breaking; RSA validation changes behavior for invalid requests. Proving tests: APDU left-pad test, RSA reject test, controlled hardware metadata/default-PIN check for retry change. Depends on / interacts with: #24 formatting. Open decisions: recommend clear public warning plus explicit documented post-operation credential rotation; decide whether to accept nonstandard short EC digests or require exact lengths.

### #27 Mismatched public/private key components (YESDK-1635) — audit severity LOW/MED
- Verdict: **CONFIRMED** | My severity: MED (trust-boundary integrity, not direct extraction of imported key).
- Location at HEAD: `src/Core/src/Cryptography/AsnPrivateKeyDecoder.cs:223-285` (audit line 227 is parser loop); RSA `:328-374`; `ECPrivateKey.cs:120-132`, `RSAPrivateKey.cs:114-131`.
- Spec / contract: “publicKey contains the elliptic curve public key associated with the private key in question.” and “Given the private key and the parameters, the public key can always be recomputed” — [RFC 5915 §3](https://www.rfc-editor.org/rfc/rfc5915#section-3). Core wrapper `ECPrivateKey.Parameters` claims “cryptographic elements needed for EC operations” (`ECPrivateKey.cs:30-38`); RSA wrapper similarly (`RSAPrivateKey.cs:30-41`).
- Reference implementations: The .NET runtime's cross-platform behavior for mismatched Q is documented as inconsistent in [dotnet/runtime #27830](https://github.com/dotnet/runtime/issues/27830); do not rely on importing inconsistent key into BCL for portable validation. Android `PivSession.java:1158-1205` accepts private values and imports only private material; returned SDK public component must not be assumed to match on-card rederived public key. `yubikey-manager/yubikit/piv.py:1350-1360` encodes EC private scalar for import; no embedded public Q consistency check in this code path. Legacy v1 command accepts private material separately (`Piv/Commands/ImportAsymmetricKeyCommand.cs`).
- Evidence: EC decoder validates point *format* (`AsnUtilities.ValidateDecodedEcPoint`), copies supplied Q into wrapper without checking Q == D·G. RSA decoder reads modulus/exponent/CRT fields then normalizes widths only, never proves n=P·Q or exponent/CRT relationships. On-card import sends private scalar/CRT, not embedded EC Q; an application consuming wrapper's reported public parameters could register unrelated B.
- Repro: `src/Core/tests/Yubico.YubiKit.Core.UnitTests/AuditV2/CoreAuditReproTests.cs:14-113`: `YESDK1635_EcPkcs8RejectsPublicPointFromDifferentPrivateScalar` and `YESDK1635_RsaPkcs8RejectsModulusUnrelatedToPrivatePrimes` both **FAILED as expected**: `Assert.Throws() Failure: No exception was thrown`. Keys are generated locally; no hardware.
- Remediation: validate imported EC embedded Q against D-derived Q using vetted curve implementation and fixed-time comparison of derived public bytes if relevant; validate RSA n=P·Q, e·d ≡ 1 mod lcm(P−1,Q−1), and DP/DQ/InverseQ relationships before producing a key wrapper; clear temporary private big-integer buffers where possible. Scope validation to private-key factories and document explicit input ownership. API impact: previously accepted malformed keys throw (`CryptographicException`), intended validation tightening. Proving tests: both newly added unit repros, plus valid-key existing decoder tests. Depends on / interacts with: #17 (derivation must not reintroduce unmanaged/managed secret leaks). Open decisions: require all RSA CRT consistency checks or only minimum mathematical checks? Recommend all.
