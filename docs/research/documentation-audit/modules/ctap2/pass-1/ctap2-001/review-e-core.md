## Required corrections

### RE-R1 — remove the remaining request/success promise from Written

**Path:** `src/Ctap2/src/Extensions/LargeBlob/LargeBlobOutput.cs:56–63`.

The new summary accurately says this is a supplied value without independent write-completion evidence. The surviving remarks still say “Only present if write was requested. Indicates whether the large blob was successfully stored.” The passive init property and synthetic-map decoder have no request context and accept any supplied `written` boolean (`:90–92`), including the registration-boolean-to-Written mapping in `ExtensionOutput.cs:189–194`. Those remarks therefore contradict both the new summary and the actual implementation. CTAP 2.3 §12.4 defines an unsigned direct-route write result, but this DTO is explicitly not that route's validated result.

**Required:** replace these remarks with the passive nullable-value meaning: null means no value was supplied/decoded; true/false reflect that supplied value, not tracked request execution or independently established storage success. Preserve the useful standard-route distinction and do not change the property, decoder, tests or wire behavior. Re-review this member and its `TryGetLargeBlob` linkage. Mapping: DOC-013/017, E-03, IMP-032.

### RE-R2 — narrow the Int64 limitation to the branches that actually read Int64

**Path:** `src/Ctap2/src/LargeBlobs/LargeBlobData.cs:39–43`, with `TryDecode:222–250` and `Encode:195–199`.

“unsigned integer values/keys beyond Int64 are not supported by the current decoder” is too broad. Integer **map keys** are decoded with `ReadInt64`, and known **origSize** uses `ReadInt64`; these fail above Int64.MaxValue. Unknown **values**, however, are retained using `ReadEncodedValue`, whose pinned implementation calls SkipValue; SkipValue reads unsigned values using `ReadUInt64`, not `ReadInt64`. For example, an otherwise conforming canonical entry with unknown integer key 99 and value UInt64.MaxValue follows the raw-value branch and is not rejected merely because that unknown value exceeds Int64. Nested unknown values follow the same skip mechanism. This is a static branch/source trace, not an executed fixture.

**Required:** state that origSize and integer map keys are limited to the signed Int64 range; unknown values retain encoded slices subject to reader/writer conformance requirements. Do not claim universal preservation, but do not erase supported unknown-value behavior either. Keep this distinct from `ExtensionOutput`, where *every reconstructed integer* really is read as Int64. Re-review entry preservation XML; future full-range engineering remains IMP-037, not an authorized fix now.

### RE-R3 — document deserialization's borrowed unknown slices

**Path:** `src/Ctap2/src/LargeBlobs/LargeBlobData.cs:340–363` (`LargeBlobArray` remarks and `Deserialize` contract); related entry remarks `:39–43`.

The constructor and init-list borrowing guidance is useful, but does not explain the materially different ownership produced by Deserialize. Known ciphertext/nonce values are copied by `ReadByteString`; unknown encoded keys/values are **views of the caller's serialized input** (`TryDecode:225,229,249`). They escape through `_unknownElements` and are later emitted by Encode. Clearing or mutating the input after Deserialize can therefore change/break a later rewrite even though known fields were copied. This is not a wholly detached decoded snapshot.

**Required:** attach an explicit borrowed-input qualification to Deserialize or its directly linked class remarks: keep the source serialized memory alive and unchanged while retained unknown elements may be used/serialized; known byte strings are independently copied while unknown encoded slices borrow the source. Existing no-full-envelope/no-universal-interoperability qualifications must remain. No clone, disposal or owner API is requested. Mapping: E-11, DOC-017, IMP-037; owner/view dependencies IMP-027/034 and C/G.

### RE-R4 — distinguish malformed encoding, wrong root type and numeric overflow

**Path:** `src/Ctap2/src/LargeBlobs/LargeBlobData.cs:353–363` (`Deserialize` exception documentation).

The corrected short/hash-error ArgumentException is accurate. The added `CborContentException` description includes “encoding/type requirements,” although a valid CBOR value of the wrong major type is an **InvalidOperationException** from ReadStartArray/ReadStartMap/typed reads; an otherwise valid integer beyond the signed range is **OverflowException** from the known origSize/integer-key ReadInt64 branches. Both escape Deserialize. The existing remarks correctly avoid claiming complete validation, but callers still need the actual error families rather than a type/encoding conflation.

**Required:** describe CborContentException as malformed/nonconforming CBOR, add the wrong-type InvalidOperationException and out-of-range OverflowException cases (or an equally explicit, locally attached error-family explanation). Do not normalize errors or add guards in this pass. Re-review Deserialize together with RE-R2. Mapping: E-11, DOC-017, IMP-037/028. Library source evidence below establishes the mechanisms; no SDK decoder was executed.
