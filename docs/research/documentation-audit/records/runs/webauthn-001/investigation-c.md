## Findings and proposed dispositions

### WA-C-001 — package landing page requires a removed PSL checker

**Priority:** required factual correction; documentation only.

**Location:** `src/WebAuthn/PACKAGE_README.md:3–8`, opening paragraphs.

The page says the client requires a “Public Suffix List backed checker” and that WebAuthn handles “origin/RP validation.” The required public option is now `RpIdValidator`, not a public-suffix predicate. Applications own syntax validity and authorization of the origin/RP pair; the SDK's RP wire checks are narrower. A caller following the package page cannot identify the required configuration and could assume the SDK supplies policy it deliberately delegates.

**Evidence:** `Client/WebAuthnClientOptions.cs`, required `RpIdValidator`; `Client/WebAuthnClient.Validation.cs:27–54`, callback and strict UTF-8 check; `IYubiKeyExtensions.cs:58–74`, required options forwarded to the client. `README.md:186–262` correctly explains the current boundary.

**Minimal change:** describe a higher-level client over CTAP2, required supported origin and required application-supplied RP validator; state the validator owns RP validity and origin/RP authorization. Do not prescribe a PSL as necessary for an exact trusted allowlist. Retain the alpha disclaimer, transitive dependency statement, installation commands and task-oriented documentation links.

**Dependencies:** module README introduction and authorization section; migration guide/map current authorization entry; root package table remains correct. Citation C1 below distinguishes browser and non-Web binding rules.

### WA-C-002 — examples stop short of a usable RP-integrated registration/authentication path

**Priority:** required consumer guidance; documentation only, not a server implementation request.

**Locations:** `src/WebAuthn/README.md` “Register a credential” (`73–94`), “Authenticate with an allow list” (`116–130`), “Client checks do not replace RP-server checks” (`257–262`), and introduction (`3–8`). Contributor “WebAuthn Client Usage” is a dependent abbreviated example.

The README locally generates both challenges and a fresh user handle, then keeps only `CredentialId`; authentication retrieves an assertion and stops. The later server-check paragraph is useful and accurate but does not explain where production options come from, how the reader completes either task, or which response bytes must reach the RP. Calling this “two calls” without this immediate context can make local credential creation/assertion retrieval appear to be completed account registration/login.

**Evidence:** creation/request options require caller-supplied challenges; `RegistrationResponse` exposes `RawAttestationObject`, `ClientData.JsonBytes`, credential ID and transport hints; `AuthenticationResponse` exposes `RawAuthenticatorData`, `Signature`, `ClientData.JsonBytes`, ID and optional `User`. `BuildRegistrationResponseAsync` and `BuildAuthenticationResponseAsync` assemble these but perform no RP-server verification or persistence. C2 requires challenges generated by the RP in its trusted environment and matched on response; C3 defines the RP-owned opaque account handle. C4/C5 require independent server verification and credential/account binding.

**Minimal change:** before the examples, explain that an RP integration obtains fresh ceremony options/challenges and a stable account-specific opaque user handle from the RP; local RNG values are demonstration-only, unless the application itself is the trusted RP. Distinguish the server's responsibilities from the client callback. After each call, explain sending the exact client-data bytes plus the appropriate response material to the RP through an application-supplied protocol, and that only successful RP verification completes registration/login. For registration, explain that the RP stores the verified credential record/public key and transport hints, not merely an unchecked local credential ID. No invented SDK JSON/server-upload helper should appear.

Add a short expected-outcome/error path in this task flow: zero matches is a normal result; required PIN/UV without an available method/prompt can fail with `NotAllowed`; an excluded credential maps to `InvalidState`; timeout is `NotAllowed`, while caller cancellation propagates `OperationCanceledException`. Note that transport/setup exceptions can propagate and do not imply another transport is retried. Link to the public error contract without claiming all failures have one type.

Preserve the existing useful RP policy examples and server-verification checklist. Prefer explicit application-owned placeholders over an unqualified local challenge generator. This is a task-completion correction, not a demand to add an RP package or exhaustive WebAuthn serializer.

### WA-C-003 — sequential examples re-register without required PIN and open overlapping clients

**Priority:** required example correction; documentation only.

**Locations:** `README.md:108–112`, “Registration transport hints”; `152–155`, PIN prompt client; `169–172`, touch client. `CLAUDE.md:93–116` similarly places direct-session and device-created clients in one scope.

The transport-hint example calls `MakeCredentialAsync(registrationOptions, pinBytes: null)` again, although the preceding options require UV and the original client has no credential prompt. The earlier borrowed PIN was cleared. A PIN-only authenticator therefore cannot satisfy this call from the documented setup; on a capable authenticator it can instead create another credential unnecessarily. The transport snapshot should be read from the original registration result.

The PIN and touch examples open additional `await using var` clients while the getting-started client is still alive if followed sequentially. The guide itself correctly states one live physical-device connection. `await using var` retains the lease until its enclosing scope ends; the new factory opens a second connection before that happens.

**Evidence:** `README.md:57–63,74–93,266–268`; `IYubiKeyExtensions.cs:69` opens the CTAP2 session; `WebAuthnClient.cs:55–65,85–91` transfers and disposes that session. `UvDecision.cs:97–123` selects a configured PIN only when PIN input is available, otherwise requires built-in UV or fails for Required.

**Minimal change:** retain the original `RegistrationResponse` in the task's intended scope and derive transport names from it. Clearly identify client-configuration examples as alternatives, preferably configure PIN/touch options before the one factory call. If demonstrating replacement, use an explicit disposal scope before reopening. Do not add a second-dispose pattern for transferred CTAP2 sessions.

**Re-review trigger:** any future connection/session ownership change reopens this example flow and README constraints together.

### WA-C-004 — authentication guidance overstates enumeration and postpones work that already finished

**Priority:** required factual correction and safe selection example.

**Locations:** `README.md:124–130`; `CLAUDE.md:140–147`; architecture “Authentication” (`140–158`) and “Non-goals” (`197–199`).

Both usage examples index `matches[0]` before handling empty results. The README says `GetAssertionAsync` returns “every credential that matched without finishing the ceremony.” This conflates two paths and two completion boundaries:

- With a nonempty allow list, `CredentialFilter` selects the first recognized descriptor and the real assertion request carries only that descriptor. The client does not promise to return every matching member of that allow list.
- With no allow list, the client can enumerate discoverable assertions with `GetNextAssertion`.
- Responses and extension results are computed eagerly before `GetAssertionAsync` returns. `SelectAsync` retrieves the cached response and performs no additional authenticator work. Its lazy wrapper is not lazy CTAP or lazy extension processing.

**Evidence:** `WebAuthnClient.Authentication.cs:104–116,138–155`; `CredentialMatcher.cs:47–75`; `MatchedCredential.cs:48–65,88–91`. No-credentials/invalid-credential statuses from the main assertion return an empty list in `CredentialMatcher`, contradicting architecture `150–153`, which says `NO_CREDENTIALS` maps to `InvalidState` here.

**Minimal change:** put count handling before indexing; explain zero, one and several matches with application-owned picker UI when needed. Explicitly separate allow-list first-match filtering from discoverable enumeration. Say that the caller selects an already-computed assertion to send to its RP; selection does not cause a second touch or postpone extension side effects. Preserve cancellation-aware waiting/idempotence without describing the public operation as unfinished device work.

**Dependencies:** WA-A public `GetAssertionAsync`/`MatchedCredential` XML and related comments, architecture page and migration `RequiresSelection` removal notes. No behavior changes proposed.

### WA-C-005 — UV guidance contains stale permissions debt, an over-absolute table, and a wrong section

**Priority:** required factual/citation correction.

**Locations:** `README.md:174–180`; `CLAUDE.md:221–245`.

The contributor guide says extension permissions are not aggregated and largeBlob writes do not contribute `LargeBlobWrite`. They are now aggregated before UV selection. The README's Discouraged row omits extension-required permissions, while both documents' unconditional Preferred/token language omits the fallback when verification is configured but cannot be supplied.

**Evidence:** `WebAuthnClient.Authentication.cs:92–101`, `Registration.cs:103–113`; each extension session's `Permissions` union; `LargeBlobProcessor.cs:90–94`; `UvDecision.cs:88–130,137–189`. In particular, configured `clientPin` without supplied PIN/prompt and without built-in UV can proceed without a token under Preferred, then escalate on `PUAT_REQUIRED`. A configured capability is not a guarantee of token acquisition.

`CLAUDE.md:237` cites WebAuthn L2 §5.4.2 for Preferred behavior. That section defines `PublicKeyCredentialRpEntity`, not UV preference. L2/L3 §5.8.6 describes Required/Preferred/Discouraged. It does not by itself prescribe this SDK's enabled-option test or fallback algorithm.

**Minimal change:** describe preference intent, distinguish “tries/obtains when available” from guaranteed token acquisition, include privileged extension permissions and the one required-UV escalation. Remove the obsolete unaggregated-permissions gap, retaining an accurate explanation of the current union. Correct the UV citation and label the SDK decision algorithm as implementation policy rather than a verbatim normative algorithm.

**Dependencies/deferred issue:** PRF has a separate standards mismatch (D1 below); do not use an improved generic UV table to imply the PRF requirement is satisfied.

### WA-C-006 — contributor guide mixes removed adapters with current processors and obsolete previewSign restrictions

**Priority:** required factual correction; preserve useful contributor context.

### WA-C-008 — extension architecture page describes obsolete flow and misattributes normative requirements

**Priority:** required coherent page update, not wholesale architecture redesign.

**Location:** complete `docs/architecture/webauthn-extension-processing.md`.

Confirmed discrepancies:

1. Vocabulary, layering tables and consequences (`20,29–62`) still use `Yubico.YubiKit.Fido2`, `FidoSession`, `IFidoSession`; current symbols are Ctap2/Ctap2Session/ICtap2Session.
2. `hmac-secret` references `§12.5` (`41–42`), but in CTAP 2.3 PS it is §12.7 (C8). The page also speaks of CTAP 2.2–2.3 in its non-goal; cite version-specific sections instead of carrying numbers across versions implicitly.
3. The type sketch (`87–103`) omits `PrepareAsync`, despite processors doing authenticator-dependent key agreement before inputs; session factory inputs also depend on creation options/effective RK or the assertion allow list. Describe actual phases without copying brittle full signatures unnecessarily.
4. Registration flow (`134–135`) says a preflight match raises `CredentialExcluded` **before any touch**. Actual preflight returns the descriptor; the main makeCredential receives it, retaining the normal UP requirement before excluded-credential failure. `Registration.cs:143–161` is direct evidence. With no token the probe omits PIN auth; with a token the shared probe signs a zero client-data hash and registration re-mints afterward (`Ceremony.cs:164–193`). Preserve both branches, not “always omit PIN auth.”
5. Authentication flow (`150–153`) incorrectly maps the main no-credentials result to `InvalidState`; see WA-C-004. The batched probe can take several round trips; “one extra round trip” (`148`) is not a general bound.
6. General unsupported-extension rule/invariant (`110–113,173`) overlooks client-derived credProps, special largeBlob handling, and actual previewSign behavior. Both factories add previewSign only if advertised, otherwise omit it, so the promised unsupported-previewSign typed error is not established by this code. See D2: distinguish a doc error about present behavior from any desired future error contract.
7. Malformed-output rule (`120–121`) names only `CborContentException`, while both session implementations also catch `InvalidOperationException`. More importantly, §9.4 does **not** contain the quoted/claimed general rule to ignore any authenticator extension output one cannot process. It defines client processing and no output for ignored extensions. General optionality/ignoring is in §9; specific extension processing can impose other requirements. Correct the citation and describe this catch behavior as SDK behavior, not a nonexistent normative quotation (C6).
8. “CTAP has only largeBlobKey + authenticatorLargeBlobs” (`45`) is too broad: CTAP 2.3 also defines the direct largeBlob extension, which this SDK page itself excludes at `197`. Say this implementation uses the largeBlobKey/storage-array path. Also, at `73`, the largeBlobKey is obtained in the assertion response, not an available pre-assertion input dependency; move that fact to the output phase.
9. The page's token permissions union is current and useful; it should be retained, reconciling the contrary module contributor guide (WA-C-005). Eager outputs while token live, fresh attempt processors, no CBOR duplicate encoding, and no UI-driven authenticator selection are also useful current explanations.

**Minimal change:** update those semantic sections together. Retain rationale for per-attempt state, wire/client layer separation and explicit non-goals. Do not reframe D1 or D2 as intentional conformance merely to remove a contradiction. Sibling APIs are analogy, not normative evidence; retain only bounded verified comparisons or pin their revisions before extending the comparison table.

### WA-C-012 — physical touch, presence evidence and transport identity should not be conflated

**Priority:** bounded terminology correction; no new OS/hardware claim.

**Locations:** README `66–67,159,182–184`; contributor `468–472`; external `src/Management/examples/ManagementTool/README.md:67` calls FIDO HID “FIDO/WebAuthn HID interface.”

The client requests user presence, but “both need a touch” and “still requires touch before reporting” are too literal across its documented HID/SmartCard/NFC scope. CTAP 2.3 terminology explicitly allows presence established by placing an authenticator into an NFC field/inserting an appropriate contact device under specified conditions; it is not universally a fresh button-touch event. This does not establish that any particular key/reader takes that path here. `SelectAsync` correctly requires no further hardware interaction.

### WA-C-013 — nonsecret credential IDs are not unconditionally safe to log

**Priority:** bounded security/privacy guidance correction, not an SDK logging-policy redesign.

**Locations:** `CLAUDE.md:373`, “Credential IDs: Public identifiers — safe to log”; dependent `README.md:278`, “Credential IDs, RP IDs, and AAGUIDs are public identifiers.”

Credential IDs are not private keys or PINs, but that does not make unrestricted disclosure harmless. WebAuthn L3 §14.6.3 explicitly explains identity-confirmation and correlation risks from exposing credential IDs. Its discussion concerns RP disclosure to unauthenticated callers, not a normative ban on SDK logging, so do not claim that it directly prohibits all logs.

**Minimal change:** retain the distinction between public protocol material and secrets, but remove blanket “safe to log.” Tell applications to treat credential/account-associated identifiers as potentially privacy-sensitive and apply their logging/redaction/access policy. Avoid adding credential contents to the illustrative log lines. Preserve the prohibition on logging PINs, keys and sensitive payloads.

**Dependencies:** module README and contributor security notes; C14. No actual logging call is being changed or audited here.

## Deferred engineering and consequential questions

### D1 — PRF's UV-dependent output is a documented deviation, not standard WebAuthn PRF behavior

**Status:** source/spec mismatch established; meaningful behavior change deferred. Coordinate with WA-B rather than independently expanding the implementation audit.

`PrfProcessor.cs:35–38` explicitly preserves the caller's UV preference and tells callers to request Required for stable results. Its `Permissions` is None (`126–127`), so requesting PRF does not otherwise force UV in the ceremony decision. In WebAuthn L3 Recommendation §10.1.4 (`#prf-extension`), the hmac-secret mapping **MUST** expose only the verified-use PRF and overrides `UserVerificationRequirement` if needed. That clause is normative and is not merely advice about output stability.

**Immediate docs limitation:** when adding the README extension overview and updating architecture, explicitly warn that this implementation currently retains the supplied UV preference; for stable verified-use results the caller must request Required. State that this differs from the standard WebAuthn PRF mapping. Do not silently brand UV-dependent output switching as a supported standards contract. Avoid claiming browser-equivalent PRF behavior.

**Engineering trigger:** an approved PRF UV-policy change plus meaningful tests reopens `PrfInput`, PRF processor/codec XML/comments, UV orchestration/options docs, README extension guidance, module contributor UV section, architecture “Where code belongs”/flow and CTAP2's hmac-secret-versus-PRF explanation. No code change in this task.

### D2 — unsupported previewSign policy: prose promises a typed error, factories omit it

Architecture `110–113` and module contributor `310–311` claim previewSign is the exception to unsupported-extension dropping. `RegistrationExtensionSession.Create:67` and `AuthenticationExtensionSession.Create:59` only add its processor when the authenticator advertises the ID. A request on an unsupported authenticator therefore does not reach that processor solely by being present. Existing processor input-validation errors do not establish an unsupported-capability error.

**Immediate docs limitation:** describe actual capability-gated omission and require callers to check the optional result before treating signing as performed, without promising an unsupported error. Keep draft/experimental qualifications. If WA-B establishes another specific call-path check, reconcile against that evidence before editing; the factory evidence here must be addressed explicitly.

**Engineering trigger:** a deliberate unsupported-capability error policy reopens session factories/tests, previewSign inputs/results XML, README overview, architecture exception/invariant and contributor guide together. Do not introduce a behavior change in this documentation cycle merely to make the prose true.
