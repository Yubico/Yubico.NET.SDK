# Core boundary inventory

This is a test-only, Core-only scanner of `src/Core/src/**/*.cs` (excluding `bin` and `obj`). It does not inspect applet projects, NativeShims, the generated native implementation, runtime behavior, or platform-specific binaries. The checked-in `core-boundaries.v1.json` is a reviewed **source-site classification**, not an async-safety attestation.

The current inventory classifies **245 sites**: 141 native imports, 3 native exports, 46 blocking waits (including native-worker parking, bounded joins, nonwaiting admission, console polling and synchronous compatibility/disposal drains), 22 scheduling sites, 22 pre-task-return dispatch gaps, 7 callback registrations, 2 runtime-native calls, 0 delegate-to-function-pointer conversions and 2 unmanaged callback addresses. Scanning complete Core at `14c90dd22`, including the verifier's known-metadata constructor, retains all 239 prior exact identities and adds six waits: constructor/GetReport/SetReport on each Windows direct facade. No prior entry is stale; removed `WindowsHidReportAccess` source contributes no retained manifest entries to delete. Facade Dispose forwards to the already-classified owner wait. The Windows native-owner/API integration from `f99cf78fe` through `378a7bb03` added 18 sites to the 218-site merged baseline; bounded runtime-completion discovery added another 3. That baseline combines upstream's 205 sites with the Linux branch's 13-site delta (-2 imports, +12 waits, +3 scheduling sites). Removing static synchronous manager shutdown and the internal monitor's synchronous stop removes two waits; complete-set PID admission adds one nonwaiting `Wait(0)` site. Owned monitors expose asynchronous disposal only, with no stop/restart API. Discovery worker entries move from `ProtocolDeviceInfo` into `SharedDeviceInfoRead` and `DiscoveryWorkerAdmission`; their exact identities follow the new containing symbols, not the old paths.

W1's independent FIDO worker directs open, overlapped submission, cancellation, retirement and checked close. Its two `Thread.Start` sites are mutually exclusive execution-context branches, not two workers. `Drain.WaitOne` is worker parking; `Dispose.GetResult` is a retained synchronous drain. `ThreadPoolBoundHandle` owns the pinned report and OVERLAPPED; immediate success and pending acceptance both require the real completion callback. The worker joins Submit return with callback **resource last use** before retirement. Cancellation, `ERROR_NOT_FOUND`, terminal wake and a completed task are not native-release evidence. Allocation-only preparation failure explicitly proves no dispatch: after allocator unwind the owner clears payload and faults the operation, then faults shared shutdown while retaining the request, uncertain BCL allocation/pin, binding, handle, root and original claim. Neither a null pointer nor this public fault authorizes Retire/Close.

W3's separate OTP worker uses zero desired access and synchronous feature GET/SET. Its two start sites are likewise mutually exclusive; its wait sites are worker parking and synchronous disposal. Pre-dispatch cancellation prevents submission; after dispatch, report storage and admission remain owned through native return, with successful payload transferred separately and staging cleared. HidD success supplies no actual byte count. The additional `OpenAsync` dispatch gap is the constructor-failure `IDisposable.Dispose` call on the transferred claim before task return: native acquisition has not started, but interface cleanup cost remains unresolved.

Runtime-completion discovery adds three exact sites in `WindowsHidReportApi`: `Open` -> `ThreadPoolBoundHandle.BindHandle`, `Submit` -> `UnsafeAllocateNativeOverlapped`, and `Retire` -> `FreeNativeOverlapped`. Callback-supplying `AllocateNativeOverlapped` and `UnsafeAllocateNativeOverlapped` invocations use `callback-registration`: allocation supplies the `IOCompletionCallback` to runtime completion tracking. Bind/free invocations use `runtime-native-call`, distinct from `native-import` declarations, with explicit per-site worker execution/lifetime reasons. The schema's existing four-part entries express both without a version change.

Recognition requires a resolved metadata `System.Threading.ThreadPoolBoundHandle` member. Nonconstant delegate arguments include method groups, callback variables and named arguments. The existing single-level managed callback-forwarder model also applies; it is a conservative candidate classifier, not callback data-flow proof. Same-named custom methods, method references without invocation, null callback constants, and the preallocated-overlapped overload do not register a callback under this rule. PreAllocatedOverlapped construction/reuse, binding Dispose, callback-body lifetime, cancellation registrations, delegate invocation in `WindowsHidOverlappedOperation.Complete`, and feature API `Transfer`/`ReleaseResources` delegates remain separately reviewed coverage limits. The scanner does not trace arbitrary nested calls or constructor-failure cleanup inside FIDO's `async` factory. No new dynamic native export sites were found.

The scanner compiles Core sources with the runtime's trusted assemblies, the test output's dependency assemblies, implicit .NET usings and the installed .NET 10 LibraryImport generator. It fails on semantic compile errors rather than falling back to text matching. Its site key is `relative-path|fully-qualified-containing-symbol|kind|fully-qualified-target|ordinal-within-that-group`; a method rename or changed target makes an entry stale. Ordinals identify repeated operations of the same kind within one method. Manifest entries carry an explicitly recorded method name plus the first 12 hex characters of the SHA-256 digest of the full key; the complete key is recomputed from source during the test. No digest or classification is generated in the passing test.

Version 1 families require an exact `path`, assigned `reviewOwner` (Core maintainer role), family `rationale`, source `evidence`, `status` (array of `outstanding`, `documented`, `implemented`, `verified`) and explicit per-site `entries`. Every native import is listed by `method#digest` and receives a family rationale plus its resolved target. Every other entry must be `method#digest#execution#justification` with execution `sync-boundary`, `async-blocked`, `worker`, or `callback`. No wildcard, directory or runtime-category waiver exists: a passing gate requires every detected site classified, no stale or duplicate sites, and valid evidence. `outstanding` is never `verified`.

Coverage is deliberately narrower than a whole-program proof. The scanner uses the .NET 10 target's preprocessor symbols, not a multi-target build evaluation; any unrecognized conditional symbol fails the scan. Native imports, selected dynamic exports, task waits/results/awaiter `GetResult` including configured awaiters, `WaitHandle.WaitOne/WaitAll/WaitAny`, `ManualResetEventSlim.Wait`, `SemaphoreSlim.Wait`, `Thread.Join`, `Thread.Sleep`, `Monitor.Wait`, scheduling, `LongRunning`, native delegate registrations, Marshal delegate conversion and address-taken `UnmanagedCallersOnly` methods are recognized by resolved symbols. Direct known blocking leaves and interface calls in task-returning methods (including generic task and value-task methods) before returning their task are reported as `dispatch-gap`; scheduled worker delegates are **not** falsely classified as caller-thread blocking. Interface dispatch alone is an unresolved gap, not proof that every implementation blocks. Other indirect dispatch, reflection, `dynamic`, indirect function-pointer calls, nested callees, conditional compilation for other targets and platform behavior need separate review. In particular the scanner cannot verify that an `async` signature does not conceal a blocking operation reached through arbitrary calls. It does not prove exception reviews are current or native cross-platform behavior.

For diagnostics, `MigrationDiagnosticsTests` parses logger calls in `PcscConnection`, `MacOSFidoHidConnection`, `MacOSOtpHidConnection`, the extracted `MacOSFidoHidNativeOwner`, `MacOSOtpHidNativeOwner`, `MacOSHidInputBridge` and `MacOSHidReportApi`, plus `PcscProtocol`, `FindHidInterfaces` and `PcscConnectionSlot`; it also uses the real logger provider for PC/SC connection, OTP recovery and APDU protocol command/response sentinel checks, including structured state and exception text. A negative result for those secrets does not make a SELECT application identifier or caller-provided exception message safe to log in every context: both have unresolved provenance. Logging in `FidoHidProtocol`, `OtpHidProtocol`, `SharedDeviceInfoRead`, `DiscoveryIdentityReader`, `FindYubiKeys`, `YubiKeyMonitor` and platform listeners still requires review of templates and externally supplied values. SDK-generated payload serialization is distinct from what an arbitrary caller logger does with supplied arguments or an external exception's own message. These tests do not establish a whole-SDK no-leak guarantee.
